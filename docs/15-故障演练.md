## 二、故障 1：`/etc/fstab` 写错（**两种形态，两种命运**）

### 2.1 这是本项最重要的发现

同一个"挂载失败"，因为**失败方式不同**，systemd 的反应完全不同：

| 形态 | 怎么造的 | `data.mount` 的状态 | 启动结果 |
|---|---|---|---|
| **Case A**：设备等不到 | 新增一条 `UUID=0badc0de-dead-beef-...0000 /mnt/lab-broken ext4 defaults 0 2` | **`inactive (dead)`**（job 被**取消**） | **降级启动**，不进 emergency |
| **Case B**：设备在但挂不上 | 把 `/data` 那行 `ext4` 改成 `xfs` 并去掉 `nofail` | **`failed`** | **`local-fs.target` 失败 → emergency** |

### 2.2 Case A 的实测（最危险的一种"正常"）

```
journalctl -b -p err:
  Nov 11 05:56:15  开机
  Nov 11 05:57:45  Timed out waiting for device dev-disk-by-uuid-0badc0de-...
                   ↑ 整整 90 秒（默认设备超时）

systemctl --failed  →  0 loaded units        ← 干干净净
mount | grep lab-broken  →  0                ← 确实没挂上
df -h /data  →  只剩 / 那一行                ← /data 真的不在
```

**`/data` 上是实验 13 的全部数据库备份。** 系统"正常启动"、服务全绿、`--failed` 为空 —— **只有一块盘悄悄消失**。

> **生产对应场景**：备份盘没挂上，备份脚本往一个空目录写（或者写到根分区，把磁盘写满）。等真需要恢复时才发现"备份都在，但在一台没挂载的机器上"。

**机制：**

```
① systemd 等 dev-disk-by-uuid-xxx.device → 等满 x-systemd.device-timeout → 超时
② device 单元超时 → 依赖它的 mount job 被【取消（cancelled）】，不是【失败（failed）】
③ data.mount 停在 inactive (dead) —— "从没成功过"的干净状态
④ local-fs.target 没有 failed 的依赖 → 跟着成功
⑤ 系统正常到达 multi-user.target
```

### 2.3 Case B 的实测（终于出了 emergency）

```bash
# 下故障
sudo cp -a /etc/fstab /root/fstab.lab15.caseB
sudo sed -i 's|/data ext4 defaults,nofail,x-systemd.device-timeout=5s 0 2|/data xfs defaults 0 2|' /etc/fstab
sudo umount /data
sudo mount -a; echo "mount -a 退出码=$?"
# → mount: /data: wrong fs type, bad option, bad superblock on /dev/sdb1
# → 退出码=32
sudo reboot
```

**重启后实测（进 emergency）：**

```
journalctl -b -1 -p err:
  Nov 11 06:27:43  systemd[1]: Failed to mount data.mount - /data.     ← failed，不是 timed out

journalctl --list-boots:
  -1  06:27:40 → 06:34:54        ← 在 emergency 里待了约 7 分钟
```

**救援路径（实测有效）：**

```
① VMware 控制台（Ctrl+Alt+Space + F1）→ 输 root 密码
② 直接 cp 备份回来：cp /root/fstab.lab15.caseB /etc/fstab
   ⚠️ 这次不需要 mount -o remount,rw / —— 因为失败的是【非根】挂载，
      systemd-remount-fs.service 早已把 / 改成可写了
   （只有当 / 本身或更早的东西失败时，/ 才是只读的 —— 那才需要 remount）
③ reboot
④ 验证：systemctl status data.mount → active (mounted)、df -h /data、6 个服务
```

### 2.4 结论修正（推翻 03 的说法）

> **03 笔记原来的说法**："没有 `nofail` 的任何 fstab 条目失败都会进 emergency mode。"
>
> **实测修正**：**不是"挂载失败"就进 emergency，而是"`mount` 单元进入 `failed` 状态"才进。** 设备**等不到**（超时）时，job 是被**取消**的，单元停在 `inactive (dead)`，**不会**拖垮启动链。

**这条已回填到 [03-磁盘分区与挂载.md](03-磁盘分区与挂载.md)。**

## 三、故障 2：磁盘被日志占满

### 3.1 下故障

```bash
# 身份：madrough @ ubuntulearn（普通用户，sudo 提权）
madrough@ubuntulearn:~$ sudo dd if=/dev/zero of=/var/log/dnsmasq.log bs=1M count=1800 status=none
madrough@ubuntulearn:~$ df -h /
/dev/mapper/ubuntu--vg-ubuntu--lv  9.8G  9.2G   33M 100% /
```

**注意服务状态：`nginx/mysql/dnsmasq/ssh` 全都还是 `active`。** 磁盘满了不会立刻让进程退出 —— 它们是在**下一次写盘时**才报错，所以症状会**分散到各处**：

| 组件 | 症状 |
|---|---|
| MySQL | `Errcode 28`、`Disk full`、binlog 写失败 |
| dnsmasq | 查询日志写不进去 |
| journald | 停止写日志（**这会让排障更难**） |
| apt | `No space left on device` |
| 应用 | `Write failed`、临时文件创建失败 |

> **这一关考的就是"症状分散、根因单一"**：能不能从一堆不相干的报错里认出"磁盘满了"。

### 3.2 三层排查法（这一关的方法论）

```
第一层：哪个文件系统满了？      df -h
第二层：满在哪个目录？          du -x -h --max-depth=1 <目录> | sort -h | tail
第三层：具体是哪个文件？        ls -lhS <目录> | head
```

**实测：**

```bash
du -x -h --max-depth=1 / | sort -h | tail -8
# 4.2G  /usr      ← 正常（系统包）
# 5.0G  /var      ← 嫌疑
# 99M   /home

du -x -h --max-depth=1 /var | sort -h | tail
# 166M  /var/cache
# 2.3G  /var/log      ← 继续钻
# 2.6G  /var/lib

du -x -h --max-depth=1 /var/log | sort -h | tail -5
# 473M  /var/log/journal
# 2.3G  /var/log

ls -lhS /var/log | head -8
# -rw-rw---- 1 dnsmasq root 1.8G Nov 11 07:35 dnsmasq.log     ← 元凶
```

**为什么不用 `find / -size +1G`**：会扫全盘（几十万文件、几分钟），还会跨挂载点跑进 `/proc`、`/data`、容器目录。**逐层下钻冷静、可控、可解释。**

**关键参数：**

| 参数 | 作用 |
|---|---|
| **`-x`** | 不跨文件系统（否则会跑进 `/data`、`/proc`、`/sys`） |
| `--max-depth=1` | 只看下一层 → 先定位方向，再钻 |
| `-h` | 人类可读 |
| `2>/dev/null` | 丢掉 `Permission denied` 噪音 |
| **`sort -h`** | 按大小排序（**不加 `-h` 会按字符串排，`900M` 会排在 `1.2G` 后面**） |
| **`ls -lhS`** | `-S` 大写 = **按大小降序**（小写 `-s` 是"按 blocks 显示"，完全不同） |

### 3.3 清理：`truncate` 而不是 `rm`（本关的坑）

**Linux 文件的三层结构：**

```
目录项（文件名） ──→ inode ──→ 数据块（真正占磁盘）
```

**`rm` 只删目录项。** inode 和数据块要等"**没有任何进程打开着它**"才释放。

所以对一个**正被进程写着的日志**执行 `rm`：

| 现象 | 原因 |
|---|---|
| `ls` 看不到文件了 | 目录项删了 |
| **`df` 空间没变** | 数据块还被进程的 fd 占着 |
| **`du` 也看不到那 1.8G** | 文件已不在目录树里，`du` 遍历不到 |

**于是出现经典矛盾：`df` 说满了，`du` 加起来却对不上。** 这时候只能用：

```bash
sudo lsof | grep deleted      # 找 "(deleted)" 标记
```

**正确做法：**

```bash
sudo truncate -s 0 /var/log/dnsmasq.log     # 长度设 0，inode 不变、fd 不变
```

| 特性 | `truncate -s 0` | `rm` |
|---|---|---|
| 空间是否立刻释放 | ✅ | ❌（进程还开着） |
| 进程能否继续写 | ✅ 同一个 inode | 写到"已删除的 inode"，看不见 |
| 需要重启服务吗 | 不需要 | 需要（否则空间永不释放） |

**等价写法**：`sudo sh -c ': > /var/log/dnsmasq.log'`（`:` 是空命令，`>` 截断打开）。

### 3.4 治本：logrotate（本关的验收硬指标）

```bash
sudo tee /etc/logrotate.d/dnsmasq > /dev/null <<'LR'
/var/log/dnsmasq.log {
    su root syslog
    daily
    rotate 7
    missingok
    notifempty
    compress
    delaycompress
    copytruncate
}
LR
```

| 指令 | 作用 |
|---|---|
| `daily` | 每天轮转（也可 `weekly`/`monthly`/`size 100M`） |
| `rotate 7` | 保留 7 个历史文件 |
| `missingok` | 文件不存在不报错 |
| `notifempty` | 空文件跳过（否则空日志也生成一堆 `.1 .2`） |
| `compress` | 旧文件 gzip |
| **`delaycompress`** | **延迟一轮再压**：刚轮转出的 `.1` 先不压（可能还有进程在写） |
| **`copytruncate`** | **先复制、再原地截断** |
| **`su root syslog`** | 切换有效身份，见下 |

#### 为什么必须 `copytruncate`

logrotate 默认是 **`mv` 改名 + 让服务重开新文件**（依赖 `postrotate kill -HUP`）。但 **dnsmasq 一直握着那个 fd 不放** —— 改名后它**继续往 `dnsmasq.log.1` 里写**，于是"新日志永远空、旧日志一直长"，**轮转等于没做**。

`copytruncate` 绕开这一点：`cp` 出副本 → **原地截断**（inode 不变）→ dnsmasq 的 fd 仍有效，下一个写操作落到"新的空文件"里。**不需要重启服务。**

**代价**：`cp` 和 `truncate` 之间有毫秒级窗口，期间写入会丢。**查询日志可以接受；审计日志不能接受**（那种必须让应用支持重开）。

#### 为什么必须 `su root syslog`

第一次 `logrotate -d` 直接报：

```
error: skipping "/var/log/dnsmasq.log" because parent directory has insecure permissions
       (It's world writable or writable by group which is not "root")
       Set "su" directive in config file to tell logrotate which user/group should be used
```

**根因**：`/var/log` 是 `drwxrwxr-x root syslog` —— **组 `syslog` 可写**（Ubuntu 为让 rsyslog 建日志这么设的）。logrotate 以 root 身份**删/建文件**，如果父目录的写权限旁落给低权组，就存在"别人在你删和建之间塞符号链接、让 root 删掉任意文件"的风险。**它宁可跳过也不冒险。**

加上 `su root syslog` 后，`-d` 输出出现：

```
switching euid from 0 to 0 and egid from 0 to 104 (pid 6319)
```

`104` 就是 syslog 的 gid —— **这就是 `su` 生效的证据**。

> **Ubuntu 上自定义 logrotate 配置十个有八个要加 `su`**，因为 `/var/log/*` 里很多目录是 `root:adm` 或 `root:syslog` 且组可写。

#### 验证

```bash
sudo logrotate -d /etc/logrotate.d/dnsmasq     # 演习：只打印不执行
sudo logrotate -f /etc/logrotate.d/dnsmasq     # 强制真跑一次
ls -l /var/log/dnsmasq.log*                     # 出现 .1
dig www.lab.test +short; systemctl is-active dnsmasq   # 服务没被打断
```

**`-d` = debug = 演习模式**，和 `rsync -n`、`netplan try` 是同一个思路：**改"会删东西"的配置前，先演习。**

## 四、故障 3：`sshd` 配置改错 → SSH 锁死

### 4.1 下故障与现象

```bash
# 注入（语法错：PermitRootLogin 只接受一个参数）
sudo tee -a /etc/ssh/sshd_config <<< 'PermitRootLogin yes yes'
sudo systemctl restart ssh; echo "退出码=$?"
```

**实测现象：**

| 观察 | 结果 |
|---|---|
| `systemctl is-active ssh` | **failed** |
| `ss -tlnp \| grep :22` | **空**（22 端口完全没在听） |
| 你现在这个 SSH 会话 | **还活着** |
| 新开窗口连接 | `Connection refused` |

**为什么老会话活着**：每个 SSH 连接是**独立的 sshd 子进程**（会话建立后与主进程无强绑定）。重启/停掉服务只影响**新连接**。

**为什么 22 完全没人听**：`ssh.socket` 与 `ssh.service` 同时持有 22（`ss` 里能看到 `sshd pid=...` 和 `systemd pid=1` 两个持有者）。服务 failed 后，socket 也随之下线（或被 systemd 关掉），于是新连接直接 `refused`。

### 4.2 `tee -a` 的陷阱（用户实测踩到）

用户的第一反应是：

```bash
echo 'PermitRootLogin yes' | sudo tee -a /etc/ssh/sshd_config
```

结果文件变成：

```
132:PermitRootLogin yes yes      ← 坏的还在
133:PermitRootLogin yes          ← 追加了一条"对的"
```

**追加不等于替换。** 而且 **`sshd` 对同一个关键字只认"第一次出现"的值** —— 所以后面加的正确值**根本不生效**，前面那行坏的照样让 `sshd -t` 报错。

> **改配置要"改原行"，不要"追加新行"。** 追加会留下两行互相矛盾的配置，谁生效取决于程序读第一个还是最后一个（sshd 读第一个，很多程序读最后一个）。这也是 `Include` / `conf.d` 目录存在的理由。

### 4.3 `sshd -t` 是第一道安全带，但它有两个坑

```bash
sudo sshd -t; echo "退出码=$?"
# /etc/ssh/sshd_config line 132: keyword PermitRootLogin extra arguments at end of line
# /etc/ssh/sshd_config: terminating, 1 bad configuration options
# 退出码=255
```

**`sshd -t` 的价值：直接告诉你"第几行、哪个词"不合法。**

**坑 1：`Missing privilege separation directory: /run/sshd`**

恢复正确配置后，`sshd -t` 仍然报错（退出码 255），但**这根本不是配置问题**：

```
Missing privilege separation directory: /run/sshd
```

`/run/sshd` 是 **`ssh.service` 的 `RuntimeDirectory=sshd`** 由 systemd 自动创建的 —— **服务在跑时才有，服务 failed/stopped 时会被删掉**。

所以：**服务已经挂了的时候，`sshd -t` 的报错会误导你。** 自救：`sudo mkdir -p /run/sshd` 再 `-t`，或者干脆先 `restart`。

**坑 2：`sshd -t` 通过 ≠ 服务能起来**

`-t` 只校验语法和配置项，不校验运行时环境（端口占用、权限、`/run` 目录、主机密钥）。**它通过之后仍然要 `restart` 并 `is-active` 确认。**

### 4.4 修复：恢复备份 ≫ 手改

```bash
sudo cp -a /root/sshd_config.lab15.bak /etc/ssh/sshd_config
sudo diff /root/sshd_config.lab15.bak /etc/ssh/sshd_config; echo "diff 退出码=$?"   # → 0
sudo sshd -t
sudo systemctl restart ssh
systemctl is-active ssh
sudo ss -tlnp | grep ':22 '
```

| 做法 | 风险 |
|---|---|
| `sed -i '132,133d'` | 行号必须正好对，改过别的行就偏了，可能删错 |
| **`cp` 备份回来** | **直接回到"已知良好"状态，不需要判断行号、不需要理解改了什么** |

**`diff` 的退出码语义**：**0 = 相同**，1 = 不同，2 = 出错。这里 0 就是"和备份完全一致"。

**正确的更改顺序（永远照这个来）：**

```
备份 → 改 → sshd -t 校验 → restart → is-active + ss 确认 → 新窗口试连
```

**②③ 必须在 restart 之前** —— 带着坏配置重启，就是把自己锁在门外。

## 五、故障 4：nginx 返回 502（五层路径）

### 5.1 下故障与现象

```bash
pkill -f 'http.server 8080'          # 杀掉后端（127.0.0.1:8080）
curl -s -o /dev/null -w "%{http_code}\n" -H "Host: lab2.test" http://127.0.0.1/
# → 502
```

**反差点**：`lab1.test`（静态）**仍 200**，只有 `lab2.test`（反代）502。

### 5.2 排查路径（本关的核心产出）

```
看到 502
 │
 ├─ ① 502 是谁报的错？
 │     nginx 作为代理，自己连不上上游 → 502 是 nginx 报的，不是后端报的
 │
 ├─ ② 先缩小范围：别的站点好吗？
 │     lab1=200、lab2=502 → nginx 进程本身没问题，问题在 lab2 的上游
 │     lab1 也挂 → 问题在 nginx 自己
 │
 ├─ ③ 看 nginx 错误日志（最快，一秒出答案）
 │     tail -6 /var/log/nginx/lab2.error.log
 │       → connect() failed (111: Connection refused)
 │         while connecting to upstream, upstream: "http://127.0.0.1:8080/"
 │       111 = ECONNREFUSED = TCP 层被拒 = 没进程听 / 端口不对
 │       ⚠️ 如果是 "upstream timed out" → 那是 504，方向完全不同
 │
 ├─ ④ 拿 upstream 地址去 ss 对照
 │     ss -tlnp | grep :8080
 │       无输出         → 后端没起（本次）
 │       只有 [::1]:8080 → 只监听 IPv6，nginx 连 127.0.0.1 会失败（隐蔽）
 │       0.0.0.0:8080   → 能连，但后端暴露给外部（安全问题，不是 502 原因）
 │
 ├─ ⑤ 绕过 nginx 直连上游（把 nginx 这一层排除）
 │     curl -o /dev/null -w "%{http_code}" http://127.0.0.1:8080/
 │       000/refused → 后端问题
 │       200         → 后端好的，问题在 nginx（proxy_pass 写错/超时/权限）
 │
 └─ ⑥ 修好后从用户视角复验
       curl -H "Host: lab2.test" http://127.0.0.1/ → 200
```

### 5.3 实测的"死亡证明"

```
2026/11/11 11:01:57 [error] 1769#1769: *1 connect() failed (111: Connection refused)
  while connecting to upstream, client: 127.0.0.1, server: lab2.test,
  request: "GET / HTTP/1.1", upstream: "http://127.0.0.1:8080/", host: "lab2.test"
```

| 字段 | 告诉你 |
|---|---|
| `(111: Connection refused)` | **TCP 层被拒**（不是超时）→ 后端不在 |
| `upstream: "http://127.0.0.1:8080/"` | **nginx 敲的是哪个门** —— 第一件要和 `ss` 对照的事 |
| `server: lab2.test` / `host:` | 哪个虚拟主机出的问题 |
| `*1` | 连接编号，能串起一次请求的全部日志 |

### 5.4 为什么"直接重启后端"这次有效、但不能当方法

| 如果 502 的真正原因是 | 重启后端有用吗 |
|---|---|
| 后端进程挂了（本次） | ✅ |
| `proxy_pass` 端口写错 | ❌ 一万次也没用 |
| 后端只听 `[::1]` | ❌ |
| 后端太慢超时 | ❌ 那是 **504** |
| nginx 无权限连上游 | ❌ |

**"猜对了"和"查出来"的区别**：猜对一次是运气。而**第 ③ 步那一行日志能让你一次锁定方向**。

## 六、故障 5：DNS 改了不生效

### 6.1 下故障与现象

```bash
# 把 www.lab.test 从 .50 改成 .222，但【故意不重启】dnsmasq
sudo sed -i 's|^host-record=www.lab.test,.*|host-record=www.lab.test,192.168.9.222|' /etc/dnsmasq.d/lab10.conf
dig +short www.lab.test @192.168.9.50     # → 192.168.9.50（旧值！）
grep -n 'www.lab.test' /etc/dnsmasq.d/lab10.conf   # → 192.168.9.222（磁盘上是新的）
```

**配置文件写 `.222`，`dig` 却返回 `.50`。**

### 6.2 机制：厨师与菜谱

| 系统里的东西 | 类比 |
|---|---|
| `/etc/dnsmasq.d/*.conf` | **菜谱**（写在纸上） |
| `dnsmasq` 进程 | **厨师** |
| 内存里的记录表 | **厨师脑子里的记忆** |

**厨师只在开工那一刻看一次菜谱，然后一直按记忆做菜。** 改了菜谱，他不会自动重看。

### 6.3 诊断方法：对比两个时间戳（关键手法）

```bash
stat -c '%y   %n' /etc/dnsmasq.d/lab10.conf
# 2026-11-11 11:21:40   /etc/dnsmasq.d/lab10.conf          ← 菜谱改动时间

systemctl show -p ExecMainStartTimestamp dnsmasq
# ExecMainStartTimestamp=Wed 2026-11-11 10:36:30 UTC        ← 厨师看菜谱的时间
```

**文件 mtime（11:21:40）> 进程启动时间（10:36:30）→ 铁证：进程没重读配置。**

> **这个手法可以迁移到任何"改了配置不生效"的场景** —— nginx、sshd、resolved、crond 全都一样：**比较"配置文件 mtime"和"进程启动时间"**。

**`stat -c '%y %n'`**：

| 部分 | 含义 |
|---|---|
| `%y` | **mtime（内容最后修改）**，人类可读 |
| `%x` | atime（最后访问） |
| `%z` | ctime（**元数据变化也算**，改权限会更新它） |
| `%n` | 文件名 |

**为什么用 `stat` 而不是 `ls -l`**：`ls -l` 只到分钟、格式固定；`stat -c` 精确到纳秒、可只取需要的字段。

### 6.4 修复与四层验证

```bash
sudo dnsmasq --test -C /etc/dnsmasq.d/lab10.conf   # ① 语法
sudo systemctl restart dnsmasq                      # ② 加载
dig +short www.lab.test @192.168.9.50               # ③ 直连 dnsmasq → .222
dig +short www.lab.test                             # ④ 经 resolved    → .222
getent hosts www.lab.test                           # ⑤ 经 nsswitch    → .222
ping -c1 www.lab.test                               # ⑥ 端到端
```

**四层递进的价值**：

| 层 | 失败说明什么 |
|---|---|
| ③ 直连 dnsmasq 失败 | dnsmasq 没加载（进程没重启/配置没被读） |
| ④ 经 resolved 失败但 ③ 成功 | **resolved 缓存**（需要 `resolvectl flush-caches`） |
| ⑤ getent 失败但 ④ 成功 | nsswitch 层（`mdns4_minimal` 等，见实验 10） |
| ⑥ ping 失败但 ⑤ 成功 | 解析没问题，是网络/主机不可达 |

**本次实测：四层全部 `.222`，没有缓存层** —— 因为 `host-record` 的 **TTL=0**，resolved 根本不会缓存它。

### 6.5 别把"清缓存"当万能药

```bash
sudo resolvectl flush-caches
sudo resolvectl statistics | head -8
```

**只有在"③ 对、④ 不对"时才需要 flush。** 一上来就 `flush-caches`，会**掩盖真正的配置问题**（比如进程根本没重读），下次换个环境照样挂。

## 七、五个故障的共同骨架（可迁移）

```
任意故障
 │
 ├─ ① 现象精确化：是超时？拒绝？502？空？—— 不同现象指向不同层
 │
 ├─ ② 分层：这台机器有哪些层？(网络/防火墙/服务/配置/进程/磁盘)
 │     然后问"哪一层变了"
 │
 ├─ ③ 拿证据，不猜：
 │     日志（journalctl -b -1 / 应用 error.log）
 │     状态（systemctl --failed / ss / mount / df）
 │     时间戳（配置文件 mtime vs 进程启动时间）
 │     退出码（但记住：0 不等于成功，见实验 13）
 │
 ├─ ④ 只改一处，改完立刻用【同一组命令】复验
 │
 └─ ⑤ 问一句"怎么防止它再发生"（logrotate / 监控 / systemd 依赖 / 备份）
```

**五个故障对应的"防复发"手段：**

| 故障 | 防复发 |
|---|---|
| fstab | 非关键挂载一律 `defaults,nofail,x-systemd.device-timeout=5s` |
| 磁盘满 | logrotate + 磁盘监控（80% 告警） |
| sshd | 改前备份 + `sshd -t` + **先在控制台确认能进** |
| 502 | 后端 `healthcheck` + 监控探测 |
| DNS 不生效 | 改完必 `restart` + 四层验证 + 配置纳入版本管理 |

## 八、踩坑清单

| # | 坑 | 说明 / 正确做法 |
|---|---|---|
| 1 | 以为"没有 nofail 的 fstab 失败 = emergency" | **只有 `mount` 单元进入 `failed` 才进 emergency**。设备**超时**时 job 被取消、单元是 `inactive(dead)`，系统**降级启动**、`--failed` 还是空的 |
| 2 | 以为降级启动就"没事" | `/data` 会**静默消失**。`df` 才看得出来。**这类故障比 emergency 更危险** |
| 3 | 进 emergency 就 `mount -o remount,rw /` | 不一定需要。失败的是**非根**挂载时，`systemd-remount-fs` 早把 `/` 改成可写了。**先试 `touch /test` 看能不能写** |
| 4 | 用 `rm` 删正被写的日志 | **空间不释放**，`df` 满但 `du` 对不上。用 **`truncate -s 0`**；`lsof \| grep deleted` 能找出来 |
| 5 | `sort` 不带 `-h` | 按字符串排序，`900M` 会排在 `1.2G` 后面。**必须 `sort -h`** |
| 6 | `ls -s` 和 `ls -S` 混用 | `-s` = 按 blocks 显示；**`-S` = 按大小降序排** |
| 7 | logrotate 报 `insecure permissions` 就放弃 | 加 **`su root syslog`**（`/var/log` 组可写） |
| 8 | logrotate 用默认 `mv` 轮转 dnsmasq 日志 | dnsmasq 不重开 fd → 新日志永远空。必须 **`copytruncate`** |
| 9 | `echo 'x' \| tee -a sshd_config` 想"改"配置 | **`-a` 是追加**。而且 **sshd 只认第一次出现的值** → 追加的正确值不生效 |
| 10 | 服务已挂时用 `sshd -t` 判断配置 | 会报 `Missing privilege separation directory: /run/sshd`（`RuntimeDirectory` 随服务消失），**掩盖真正的错误** |
| 11 | 改 sshd 后直接 restart | 必须 **备份 → `sshd -t` → restart → `is-active` + `ss` → 新窗口试连** |
| 12 | 502 就重启后端 | 后端挂了才行。`proxy_pass` 写错/只监听 `[::1]`/超时（是 504）都不会因此好转。**先看 error.log** |
| 13 | 改了配置不生效就 `flush-caches` | 大多数情况是**进程没重读配置**。先用 **mtime vs 进程启动时间**对比 |
| 14 | 只测 `dig` 就宣布 DNS 修好 | 要四层都测：`dig @服务器` / `dig` / `getent` / `ping` |
| 15 | 靠"重启一下"当修复手段 | 结果达成 ≠ 找到根因。**下次同样故障照样挂** |

## 九、命令详解（本项首次出现）

| 命令 / 参数 | 是什么 → 干什么 → 为什么这里用 |
|---|---|
| `du -x -h --max-depth=1 DIR` | 统计目录占用。**`-x` 不跨文件系统**、`--max-depth=1` 只看下一层 → 逐层下钻找大目录 |
| `sort -h` | 按人类可读大小排序（`1.2G` > `900M`）→ **不加会按字符串排，结果错** |
| `ls -lhS` | `-S` **按大小降序**（大写）；`-s` 是"显示 blocks" |
| `stat -c '%y %n'` | 自定义格式输出文件时间。`%y`=mtime、`%x`=atime、`%z`=ctime → 精确对比时间戳 |
| **`truncate -s 0 FILE`** | 把文件长度设为 0，**inode 与 fd 不变** → 释放空间但进程仍可写 |
| `lsof \| grep deleted` | 找"已删除但仍被进程打开"的文件 → 解释 `df` 与 `du` 对不上的情况 |
| `install -m 755` | 复制 + 设权限 + 设属主（先写临时文件再 rename） |
| **`logrotate -d CONFIG`** | **debug/演习**：只打印会做什么，不动文件 → 改"会删东西"的配置前必做 |
| `logrotate -f CONFIG` | **force**：忽略时间条件强制轮转一次 → 测试配置是否真能工作 |
| `sshd -t` | 校验 sshd 配置语法与参数，**报错带行号** → 改完 sshd 的第一道安全带 |
| `systemctl show -p ExecMainStartTimestamp UNIT` | 打印单元的**主进程启动时刻** → 和配置文件 mtime 对比，判断"进程有没有重读配置" |
| `curl -s -o /dev/null -w '%{http_code}'` | 只输出 HTTP 状态码 → 判断站点状态最干净的方式（`000` = 没拿到响应） |
| `curl -H 'Host: X' http://127.0.0.1/` | 手工指定 Host 头 → 无需 DNS 就能测指定虚拟主机（实验 08） |
| **`pkill -f 'PATTERN'`** | `-f` 匹配**完整命令行** → 比 `pkill 名字` 精确，不会误伤 |
| `journalctl -b -1` | **上一次开机**的日志（`0`=本次，`-1`=上次）→ 查"刚才那次失败"的证据 |
| `journalctl --list-boots` | 列出所有开机记录（编号/ID/起止时间）→ 知道能往回查几次 |

**诚实的自我评估：**

> **5 个故障里，只有 1 个是独立完成的。** 故障 2/3/5 是在提示下看懂并执行，故障 4 是"猜对了层"。
>
> 这说明：**知识结构有了（知道该看哪儿），但独立排障的肌肉记忆还没形成。** 第二次必须无提示重做，否则这一关在面试里会露馅。

**面试可用的一句话：**

> 我做过一轮五个故障的演练：fstab 写错、磁盘被日志占满、sshd 配置改错、nginx 502、DNS 改了不生效。最有价值的发现是 **fstab 有两种失败形态**——设备等不到时 systemd 会把 mount job **取消**，单元是 `inactive(dead)`，系统**降级启动**、`/data` 静默消失、`--failed` 还是空的；只有 mount 单元真的 `failed` 时才会进 emergency。磁盘那关学到 `rm` 不释放被进程打开的文件、必须 `truncate`，以及 logrotate 对不重开日志的守护进程要用 `copytruncate`；sshd 那关学到"追加配置行"是错的（sshd 只认第一个）和 `sshd -t` 在服务已挂时会被 `/run/sshd` 误导；502 关的路径是"先看 error.log 的 111 和 upstream 地址，再用 `ss` 对照，最后绕过 nginx 直连上游"。
