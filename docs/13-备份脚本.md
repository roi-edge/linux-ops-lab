## 一、目标与验收

**做：** 写脚本：`mysqldump` + 打包 + 按日期命名 + 只保留 7 天；用 `cron` 每天跑

**验收：** **删掉一天的数据，能用备份恢复出来**

**结论：** 达成，而且做的是**最坏情况** —— `DROP DATABASE labdb` 把整个库删掉，用一个 13K 的备份文件完整还原，指纹（`COUNT=1000`、`SUM(id)=500500`、时间跨度、具体行值）逐项对上。

过程中撞到三个经典坑：① `mysqldump` **打印 Error 却退出码 0**；② **crontab 里的 `%` 是特殊字符**；③ **管道会掩盖 mysqldump 的失败**（`pipefail` 的作用）。

## 二、最终状态

### 2.1 备份脚本

```bash
# 身份：madrough @ ubuntulearn（查看用）
madrough@ubuntulearn:~$ sudo cat /usr/local/bin/mysql-backup.sh
```

```bash
#!/usr/bin/env bash
set -euo pipefail
DIR=${DIR:-/data/backup/mysql}; DAYS=${DAYS:-7}; DB=${DB:-labdb}
LOG=/var/log/mysql-backup.log; E=$(mktemp)
F="$DIR/${DB}_$(date +%Y%m%d_%H%M%S).sql.gz"
say(){ echo "$(date '+%F %T') $*" | tee -a "$LOG"; }
trap 'rm -f "$E"' EXIT
mkdir -p "$DIR"; say "start $DB"
mysqldump --defaults-extra-file=/etc/mysql/backup.cnf --single-transaction --quick \
  --routines --triggers --events --no-tablespaces --databases "$DB" 2>"$E" | gzip -9 >"$F"
if grep -qi error "$E"; then say "FAIL: $(tr '\n' ' ' <"$E")"; rm -f "$F"; exit 1; fi
chmod 600 "$F"; gzip -t "$F"
if ! zcat "$F" | tail -3 | grep -q 'Dump completed'; then say "FAIL: incomplete"; rm -f "$F"; exit 1; fi
say "ok $(du -h "$F" | cut -f1)"
find "$DIR" -maxdepth 1 -name "${DB}_*.sql.gz" -mtime +$((DAYS-1)) -print -delete | while read -r x; do say "del $(basename "$x")"; done
say "done, keep $(find "$DIR" -name "${DB}_*.sql.gz" | wc -l)"
```

**安装位置与权限**：`/usr/local/bin/mysql-backup.sh`，**`755 root:root`**（只有 root 能改，任何人能执行）。

| 项 | 值 |
|---|---|
| 备份目录 | **`/data/backup/mysql/`**（`/data` 是独立的 2G ext4，和根分区隔离） |
| 备份文件 | `labdb_YYYYmmdd_HHMMSS.sql.gz`，**`600 root:root`** |
| 单文件大小 | 约 **13K**（未压缩 48K，压缩比约 3.7:1） |
| 日志 | `/var/log/mysql-backup.log`（`tee -a` 同时打屏幕和文件） |
| 凭证 | `/etc/mysql/backup.cnf`（`600 root`，含 `bkp` 账号密码，**脚本里不出现密码**） |
| 备份账号 | `'bkp'@'localhost'`，权限 `SELECT, LOCK TABLES, SHOW VIEW, EVENT, TRIGGER` |

## 三、操作步骤（按真实顺序）

### 3.1 摸底

```bash
# 身份：madrough @ ubuntulearn（普通用户，sudo 提权）
madrough@ubuntulearn:~$ uptime
madrough@ubuntulearn:~$ df -h / /data | tail -3
madrough@ubuntulearn:~$ findmnt /data -o TARGET,SOURCE,FSTYPE,SIZE,AVAIL
madrough@ubuntulearn:~$ systemctl is-active cron mysql dnsmasq
madrough@ubuntulearn:~$ mysqldump --version
```

**实测：**

```
up 2 min                                  # 距上次实验隔了 23 小时，重启过
/  9.8G  7.3G  2.1G  79%                  # 根分区只剩 2.1G
/data  /dev/sdb1  ext4  2.0G  1.8G avail   # 独立挂载，1% 使用
cron/mysql/dnsmasq 全 active
mysqldump Ver 8.0.46
```

**为什么备份要放 `/data` 而不是 `/`**：根分区只剩 2.1G，而且 **`/data` 是独立块设备**——备份撑爆 `/data` 不会影响系统启动，根分区写满则会让 MySQL、日志、甚至 `sshd` 全部异常。**"备份不能和数据抢同一个文件系统"是基本要求**。

### 3.2 造可验证的数据集

```bash
# 身份：madrough @ ubuntulearn（普通用户，sudo 提权）
madrough@ubuntulearn:~$ sudo mysql <<'SQL'
SET SESSION cte_max_recursion_depth = 100000;
CREATE TABLE IF NOT EXISTS labdb.orders (
  id INT AUTO_INCREMENT PRIMARY KEY,
  customer VARCHAR(32) NOT NULL,
  amount DECIMAL(10,2) NOT NULL,
  created_at DATETIME NOT NULL,
  KEY idx_created (created_at)
) ENGINE=InnoDB;

INSERT INTO labdb.orders (customer, amount, created_at)
WITH RECURSIVE seq AS (
  SELECT 1 AS n UNION ALL SELECT n + 1 FROM seq WHERE n < 1000
)
SELECT CONCAT('cust-', n), ROUND(1 + RAND() * 999, 2), NOW() - INTERVAL n MINUTE
FROM seq;

SELECT COUNT(*) AS 行数, MIN(created_at), MAX(created_at) FROM labdb.orders;
SQL
```

**实测：1000 行，时间跨度 `2026-11-08 14:57:43` ~ `2026-11-09 07:36:43`。**

**为什么要造数据**：验收是"删了能恢复"，库里只有 1 行时，删了再恢复看不出任何差别。**造 1000 行有规律（`cust-N`）+ 有随机值（`amount`）+ 有时间跨度**，恢复后才能用指纹证明"是同一批数据"。

### 3.3 建备份专用账号（最小权限）

```bash
# 身份：madrough @ ubuntulearn（普通用户，sudo 提权）
madrough@ubuntulearn:~$ sudo mysql <<'SQL'
CREATE USER 'bkp'@'localhost' IDENTIFIED BY '<BACKUP_PASSWORD>';
GRANT SELECT, LOCK TABLES, SHOW VIEW, EVENT, TRIGGER ON *.* TO 'bkp'@'localhost';
SQL
```

| 权限 | 用途 |
|---|---|
| `SELECT` | 读表数据 |
| `LOCK TABLES` | 不用 `--single-transaction` 时靠它保证一致性 |
| `SHOW VIEW` | dump 视图定义 |
| `EVENT` | dump 定时事件（`--events`） |
| `TRIGGER` | dump 触发器（`--triggers`） |

**故意不给**：`INSERT/UPDATE/DELETE/DROP`（备份账号只读）、`FILE`（能读写服务器任意文件，高危）、`SUPER`/`PROCESS`（见 3.5）。

### 3.4 凭证文件（脚本里不出现密码）

```bash
# 身份：madrough @ ubuntulearn（普通用户，sudo 提权）
madrough@ubuntulearn:~$ sudo tee /etc/mysql/backup.cnf > /dev/null <<'EOF'
[client]
user=bkp
password=<BACKUP_PASSWORD>
host=localhost
EOF
madrough@ubuntulearn:~$ sudo chmod 600 /etc/mysql/backup.cnf
```

**`host=localhost` 让 mysqldump 走 Unix socket** → 才匹配得上 `'bkp'@'localhost'`（实验 12 的 4.3：`localhost` 只属于 socket）。

### 3.5 `mysqldump` 报错但退出码 0（第一个坑）

```bash
# 身份：madrough @ ubuntulearn（普通用户，sudo 提权）
madrough@ubuntulearn:~$ sudo mysqldump --defaults-extra-file=/etc/mysql/backup.cnf \
  --single-transaction --quick --routines --triggers --events \
  --databases labdb > /tmp/labdb_test.sql
mysqldump: Error: 'Access denied; you need (at least one of) the PROCESS privilege(s)
for this operation' when trying to dump tablespaces
madrough@ubuntulearn:~$ sudo mysqldump ...同样的参数... > /dev/null; echo "退出码=$?"
mysqldump: Error: '...PROCESS privilege...' when trying to dump tablespaces
退出码=0                                      ← ★ 报错了，但退出码是 0
```

**而实际产物是好的**：48K、2 条 `INSERT INTO`、结尾有 `-- Dump completed`。

| 判据 | 结果 |
|---|---|
| 看输出有没有 `Error` | ❌ 会误判（本次是真成功却打 Error） |
| 看退出码 | ❌ 会漏判（本次 Error 却退出 0） |
| **看产物完整性** | ✅ 唯一可靠 |

> **这是本项最重要的认知：备份脚本不能靠"退出码 0"就当成功，也不能靠"没打印错误"就当成功。**

**根因与修法**：MySQL 8 的 `mysqldump` 默认要 dump **表空间（tablespace）**信息，读 `INFORMATION_SCHEMA.FILES` 需要 `PROCESS` 权限。

| 修法 | 评价 |
|---|---|
| **`--no-tablespaces`** | ✅ **采用**。我们没有"通用表空间"，跳过它零损失，且**不必把 `PROCESS` 这种能看到全部会话 SQL 的权限给备份账号** |
| 给 `bkp` 加 `PROCESS` | 能跑通，但权限过大 |
| 改用 root | 最省事最危险 |

**加了 `--no-tablespaces` 后：无报错、退出码 0。**

### 3.6 写脚本

```bash
# 身份：madrough @ ubuntulearn（普通用户，不需要 sudo）
madrough@ubuntulearn:~$ cat > /tmp/mysql-backup.sh <<'SCRIPT'
...（见 2.1）...
SCRIPT
madrough@ubuntulearn:~$ sudo install -m 755 /tmp/mysql-backup.sh /usr/local/bin/mysql-backup.sh
madrough@ubuntulearn:~$ bash -n /usr/local/bin/mysql-backup.sh && echo "语法 OK"
```

**`bash -n`**：只做语法检查、不执行 → 长脚本写完第一件事。

**`install -m 755`** 比 `cp + chmod` 好：一条命令完成复制+权限+属主，且**先写临时文件再 rename**，不会出现"被读到半个文件"。

### 3.7 手工跑一次并验证产物

```bash
# 身份：madrough @ ubuntulearn（普通用户，sudo 提权）
madrough@ubuntulearn:~$ sudo /usr/local/bin/mysql-backup.sh
2026-11-09 08:15:22 start labdb
2026-11-09 08:15:22 ok 16K
2026-11-09 08:15:22 done, keep 1

madrough@ubuntulearn:~$ sudo ls -l /data/backup/mysql/
-rw------- 1 root root 13290 Nov  9 08:15 labdb_20261109_081522.sql.gz

madrough@ubuntulearn:~$ sudo zcat /data/backup/mysql/labdb_*.sql.gz | grep -o 'cust-' | wc -l
1000
madrough@ubuntulearn:~$ sudo zcat /data/backup/mysql/labdb_*.sql.gz | grep -c 'INSERT INTO'
2
```

**`grep -c` 和 `grep -o | wc -l` 的区别（实测踩过）**：

| 命令 | 数的是 | 本次结果 |
|---|---|---|
| `grep -c 'cust-'` | **匹配的行数** | **1**（因为 extended-insert 把 1000 行塞在**同一行**里） |
| `grep -o 'cust-' \| wc -l` | **匹配出现的次数** | **1000** ✅ |
| `grep -c 'INSERT INTO'` | INSERT 语句条数 | **2** |

**这就是"1 个文件 / 2 条 INSERT / 1000 行数据"的三层结构**：`--extended-insert`（默认开）把多行合并成一条长 INSERT，所以**文件小、恢复快**，但**行数要用 `-o` 才数得出来**。

### 3.8 轮转测试（伪造 mtime）

```bash
# 身份：madrough @ ubuntulearn（普通用户，sudo 提权）
madrough@ubuntulearn:~$ for d in 2 5 6 7 10; do
  t=$(date -d "-$d days" +%Y%m%d_%H%M%S)
  sudo cp -p /data/backup/mysql/labdb_20261109_081522.sql.gz "/data/backup/mysql/labdb_${t}.sql.gz"
  sudo touch -d "-$d days" "/data/backup/mysql/labdb_${t}.sql.gz"
done
madrough@ubuntulearn:~$ ls -l --time-style=long-iso /data/backup/mysql/
```

**造出 6 个文件（10/7/6/5/2 天前 + 今天），然后跑脚本：**

```
2026-11-09 08:52:32 del labdb_20261030_083646.sql.gz     ← 10 天，删
2026-11-09 08:52:32 del labdb_20261102_083646.sql.gz     ← 7 天，删
2026-11-09 08:52:32 done, keep 5
```

**保留 `20261103`（6 天）**，删掉 `20261030`（10 天）和 `20261102`（7 天）—— **边界完全正确**。

**`-mtime` 的精确语义（差一天就出错）：**

| 表达式 | 含义 |
|---|---|
| `-mtime 6` | 年龄的**整 24 小时数向下取整恰好等于 6** |
| `-mtime +6` | **超过 6 整天**，即 **≥ 7 天** |
| `-mtime -6` | 不到 6 天 |

**保留 7 天 → 写 `-mtime +6`**：删除"7 天及以上"的，剩下今天+前 6 天 = 7 天。写成 `+7` 就变 8 天。

**验证 cron 真的会执行（不能只看文件写了没）**：

```bash
# 身份：madrough @ ubuntulearn（普通用户，sudo 提权）
madrough@ubuntulearn:~$ sudo tee /etc/cron.d/lab13-crontest > /dev/null <<'CRON'
* * * * * root date -u >> /tmp/cron-alive.txt
* * * * * root date '+\%F \%T' >> /tmp/cron-pct.txt
CRON
madrough@ubuntulearn:~$ sudo chmod 644 /etc/cron.d/lab13-crontest
madrough@ubuntulearn:~$ sudo rm -f /tmp/cron-alive.txt /tmp/cron-pct.txt
madrough@ubuntulearn:~$ sleep 80
madrough@ubuntulearn:~$ cat /tmp/cron-alive.txt /tmp/cron-pct.txt
```

**实测：**

```
Mon Nov  9 11:19:01 AM UTC 2026      ← date -u（无 %），正常
Mon Nov  9 11:20:01 AM UTC 2026
2026-11-09 11:19:01                  ← '+\%F \%T'（转义 %），正常
2026-11-09 11:20:01
```

**两个坑（都是实测撞到的）：**

| # | 坑 | 说明 |
|---|---|---|
| 1 | **crontab 里的 `%` 是特殊字符** | 第一个未转义的 `%` 表示"命令结束"，后面全部变成命令的 **stdin**。所以 `date '+%F %T'` 实际执行的是 `date '+` → **失败、文件不生成、cron 发本地邮件（没 MTA 就静默丢弃）**。**必须写成 `\%`** |
| 2 | **`!!` 在 bash 里是历史展开** | 我写的 `echo "!! 文件不存在"` 被展开成**上一条命令原文**。字符串里别用 `!!` |

**cron 权限要求（不合格就静默忽略，不报错）：**

| 项 | 要求 |
|---|---|
| 属主 | `root:root` |
| 权限 | `644`（**组/其他人不能有写权限**） |
| 文件名 | 别带扩展名点 |
| 结尾 | 必须有换行 |

**为什么显式写 `SHELL` 和 `PATH`**：cron 的默认 PATH 极简（常只有 `/usr/bin:/bin`）、默认 `SHELL=/bin/sh`。**"手工跑正常、cron 跑报 command not found"就是死在这里**。

**`/etc/cron.d` 的文件格式比 `crontab -e` 多一列（user）：**

```
30  2  *  *  *  root  /usr/local/bin/mysql-backup.sh
└───┬──┘        └─┬┘  └──────────┬───────────────┘
 5 个时间字段   跑的用户        命令
```

### 3.10 恢复演练（最坏情况）

```bash
# 身份：madrough @ ubuntulearn（普通用户，sudo 提权）
madrough@ubuntulearn:~$ sudo mysql -e "SELECT COUNT(*) AS 事故前行数 FROM labdb.orders;"
madrough@ubuntulearn:~$ sudo mysql -e "DROP DATABASE labdb;"
madrough@ubuntulearn:~$ sudo mysql -e "SHOW DATABASES LIKE 'labdb';"      # Empty set
madrough@ubuntulearn:~$ sudo mysql -e "SELECT COUNT(*) FROM labdb.orders;"
ERROR 1049 (42000): Unknown database 'labdb'
```

**恢复：**

```bash
# 身份：madrough @ ubuntulearn（普通用户，sudo 提权执行整条管道）
madrough@ubuntulearn:~$ sudo sh -c 'zcat /data/backup/mysql/labdb_20261109_112214.sql.gz | mysql'
madrough@ubuntulearn:~$ sudo mysql -e "SELECT COUNT(*) AS n, SUM(id) AS sum_id, MIN(created_at) AS t_min, MAX(created_at) AS t_max FROM labdb.orders;"
```

**实测（与 3.2 的指纹逐字一致）：**

```
n = 1000    sum_id = 500500
t_min = 2026-11-08 14:57:43    t_max = 2026-11-09 07:36:43
cust-1/551.71    cust-2/133.21    cust-3/8.91
```

**为什么用 `sudo sh -c 'zcat ... | mysql'`：**

| 写法 | 谁执行 | 结果 |
|---|---|---|
| `sudo zcat f \| mysql` | zcat=root，**mysql=普通用户** | 失败（auth_socket 不认） |
| **`sudo sh -c 'zcat f \| mysql'`** | **整条管道交给 root 的 shell** | ✅ |

**原理**：管道 `|` 和重定向 `>` 都由**当前 shell** 建立，`sudo` 只作用于紧挨着的那个命令。**和实验 11 的 `sudo echo > file` 是同一件事。**

**`DROP DATABASE` 之后授权不丢**（实测 `SHOW GRANTS` 里 `GRANT ... ON labdb.*` 还在）：授权按**库名字符串**匹配，不按对象是否存在。所以恢复建库后权限**自动回来**。

## 四、原理

### 4.1 逻辑备份 vs 物理备份

| | **逻辑备份（`mysqldump`，本项用的）** | **物理备份（`xtrabackup` / 文件拷贝）** |
|---|---|---|
| 产物 | SQL 文本（可读、可编辑、可挑表恢复） | 数据文件二进制副本 |
| 速度 | 慢（要序列化成 SQL） | 快 |
| 体积 | 小（压缩后尤其小） | 大（等同数据目录） |
| 跨版本 | ✅ 能跨大版本迁移 | ❌ 基本只能同版本 |
| 适用 | **几十 G 以下、需要跨版本/挑表恢复** | 大库、要求最短备份窗口 |
| 本项数据 | 48K 未压缩 / **13K 压缩** | — |

### 4.2 `--single-transaction` 为什么能"不锁表还一致"

InnoDB 支持 **MVCC**。`mysqldump --single-transaction` 做的第一件事是：

```sql
START TRANSACTION WITH CONSISTENT SNAPSHOT;
```

之后**整个 dump 期间读的都是这个快照**，业务端照样写入，互不阻塞。所以：

| 条件 | 说明 |
|---|---|
| 表必须是 **InnoDB** | **MyISAM 不支持事务**，`--single-transaction` 对它无效，还是会锁 |
| 不能有 DDL 并发 | dump 期间别人 `ALTER TABLE` 会导致 dump 报错/不一致 |

### 4.3 为什么必须 `set -o pipefail`

```bash
mysqldump ... | gzip -9 > out.gz
```

| 情况 | 不加 `pipefail` | 加了 `pipefail` |
|---|---|---|
| mysqldump 失败、gzip 成功 | **退出码 0**（只看最后一个命令）→ 你得到一个 20 字节的"成功"备份 | **退出码非 0** → 脚本中止 |

**这是备份脚本里最隐蔽的 bug**：备份文件存在、非空、甚至 `gzip -t` 都能过（空输入压出来是合法的 gzip），**但它里面一句话都没有**。

### 4.4 三层校验（本项的校验策略）

| 层 | 手段 | 能发现什么 |
|---|---|---|
| ① 退出码 | `set -euo pipefail` + `if ! ...; then` | 命令失败、管道任一环失败 |
| ② stderr 内容 | `grep -qi error "$E"` | **"报错但退出 0"**（本次实测存在） |
| ③ 产物完整性 | `gzip -t` + `zcat \| tail \| grep 'Dump completed'` | **截断**（OOM/磁盘满/超时被打断） |

**为什么第③层必须看 `Dump completed`**：`mysqldump` 被打断时，**前面的输出完全正常**，只有结尾缺这一行。文件大小、`gzip -t` 都可能通过。

### 4.5 cron 的四种放法

| 位置 | 格式 | 适用 |
|---|---|---|
| `crontab -e`（用户级） | 5 字段 + 命令（**无 user 列**） | 某个用户自己的任务 |
| `/etc/crontab` | 5 字段 + **user** + 命令 | 系统总表，**别直接改** |
| **`/etc/cron.d/*`** | 5 字段 + **user** + 命令 | **推荐**：按功能拆文件，删文件即下线，`apt` 升级不碰 |
| `/etc/cron.{hourly,daily,…}` | 放可执行脚本 | 粒度粗，不能指定时刻 |

### 4.6 备份的"3-2-1"原则（生产必备，本项未做）

| 数字 | 含义 | 本项状态 |
|---|---|---|
| **3** 份副本 | 生产 + 2 份备份 | ❌ 只有 1 份在本机 |
| **2** 种介质 | 例如本机磁盘 + 对象存储/NAS | ❌ 单一介质 |
| **1** 份异地 | 至少一份在另一个地理位置 | ❌ 无 |

**本项只做到了"有备份"，离"能扛灾难"还差得远** —— 如果 `/data` 这块盘坏了（或者虚拟机没了），备份和数据一起消失。这一条必须写清楚，见第五节。

## 五、生产实践（实际工作中的正确做法）

> 承接实验 12 第五节。备份这件事，"能生成文件"只是起点。

### 5.1 备份账号：只读 + 最小权限

```sql
CREATE USER 'backup'@'localhost' IDENTIFIED BY '<强密码>';
GRANT SELECT, LOCK TABLES, SHOW VIEW, EVENT, TRIGGER ON *.* TO 'backup'@'localhost';
-- 按需再加：RELOAD（--flush-logs）、REPLICATION CLIENT（--master-data）
```

| 禁止 | 原因 |
|---|---|
| 用 `root` 跑备份 | 脚本被改一行就能拖库；且无法审计"谁在用超级权限" |
| 给备份账号 `FILE` | 能读写服务器任意文件，等于半个 root |
| 给 `PROCESS`（为了去掉那条 tablespace 报错） | 能看到**所有会话正在执行的 SQL**。**正确做法是 `--no-tablespaces`** |
| 给写权限 | 备份账号永远不需要写 |

### 5.2 密码不进命令行、不进脚本

| ❌ | ✅ |
|---|---|
| `mysqldump -p'密码'` | `--defaults-extra-file=/etc/mysql/backup.cnf`（**600 root**） |
| 密码写在脚本里 | `mysql_config_editor set --login-path=backup --password` → `--login-path=backup` |
| 备份文件 644 | **`chmod 600`**（备份含全部数据，等于明文数据库） |

### 5.3 必须做三重校验（本项已实现）

```bash
set -euo pipefail                              # ① 退出码
grep -qi error "$ERRLOG"                       # ② stderr
gzip -t "$F"                                   # ③ gzip 完整
zcat "$F" | tail -5 | grep -q 'Dump completed'  # ③ 内容完整
```

**更严格的一次性校验（`mysqlcheck` / 恢复演练）：**

```bash
# 真正验证：把备份恢复到临时实例或临时库
sudo sh -c 'zcat backup.sql.gz | mysql'
mysql -e "CHECKSUM TABLE labdb.orders"      # 和源库比对
```

### 5.4 保留策略：不是"7 天"而是"分层"

真实的保留策略通常是 **GFS（Grandfather-Father-Son）**：

| 层 | 保留 | 用途 |
|---|---|---|
| 日备 | 7~14 天 | 恢复"误删/误改" |
| 周备 | 4~8 周 | 恢复"上周就发现错了" |
| 月备 | 12 个月 | 审计、合规 |

**本项只做了日备 7 天**，够验证逻辑，不够生产。

### 5.5 3-2-1 + 异地 + 防勒索

| 要求 | 做法 |
|---|---|
| **3 份副本** | 生产库 + 本机备份 + 远端备份 |
| **2 种介质** | 本机磁盘 + 对象存储（S3/OSS）或 NAS |
| **1 份异地** | 不同机房/可用区（防火灾、防整机报废） |
| **不可变存储** | 开对象存储的 **WORM / 版本控制**，防勒索软件加密备份 |
| **离线副本** | 定期离线/磁带副本，防"删库跑路"和勒索 |

> **本项最大的缺口就在这里**：备份和数据在同一块 `/data` 盘上。**盘坏 = 数据 + 备份一起没。**

### 5.6 备份文件要加密

备份 = 整个库的明文。传输（传到对象存储/异地）和静态存储都可能泄露：

```bash
# 传输加密
gzip -c dump.sql | openssl enc -aes-256-cbc -salt -pbkdf2 -out dump.sql.gz.enc
# 或直接交给对象存储的服务端加密（SSE-KMS）
```

**密钥不能和备份放在一起**（否则等于没加密）。

### 5.7 恢复演练必须定期做（"没验证过的备份等于没有"）

| 频率 | 内容 |
|---|---|
| **每月** | 抽一个备份，恢复到**临时实例**，跑 `CHECKSUM TABLE` 或关键业务查询比对 |
| **每季度** | 完整灾难演练：从"库被删"到"业务可用"计时 |
| 上线前 | 大版本升级/迁移前必须演练一次恢复 |

**只备份不演练，等于赌运气**：真正出事那天才发现"备份是空的""权限不对""恢复脚本跑不通"，那才是最惨的。

### 5.8 监控"备份是否成功"（不能只看 cron 跑了没）

| 手段 | 说明 |
|---|---|
| **检查最新备份的时间戳** | 如果最新备份超过 26 小时 → 告警（实验 24 会做类似规则） |
| **检查退出码/日志里的 FAIL** | 脚本里已经区分 `ok` / `FAIL` |
| **检查文件大小异常** | 突然变小（比如从 13K 变 200 字节）说明 dump 失败但脚本没拦住 |
| **dead man's switch** | 备份成功后上报心跳（如 healthchecks.io），**心跳消失就告警** —— 能发现"任务根本没跑" |

**cron 不会告诉你"任务失败了"**（它只发本地邮件，而服务器通常没配 MTA）。**必须有独立的监控。**

### 5.9 增量备份与 binlog

`mysqldump` 是**全量**。生产上通常：

| 类型 | 工具 | 频率 |
|---|---|---|
| 全量 | `mysqldump` / `xtrabackup` | 每天 |
| 增量 | `xtrabackup --incremental` | 每小时 |
| **时间点恢复（PITR）** | **binlog**（`--master-data` + `mysqlbinlog`） | 连续 |

**`binlog` 是"恢复到误删前一秒"的唯一手段**，前提是 `log_bin=ON` 且备份里记录了 binlog 位点（`--master-data=2` / `--source-data=2`）。**本项未做**。

### 5.10 备份的其它注意点

| 项 | 说明 |
|---|---|
| **备份窗口** | 避开业务高峰；`--single-transaction` 虽不锁表，但**大量读会拖慢磁盘** |
| **备份对 IO 的影响** | 大库 dump 会产生持续读压力，可用 `--compress`（传输压缩）或限速 |
| **`--single-transaction` 只对 InnoDB 有效** | MyISAM 表会被锁，必须单独考虑 |
| **别忘 `--routines --events --triggers`** | 默认不全导，**恢复后发现存储过程没了**是经典事故 |
| **字符集** | 用 `--default-character-set=utf8mb4`，避免恢复时乱码 |
| **`--set-gtid-purged=OFF`** | 开了 GTID 的环境，不加这参数恢复会冲突 |

## 六、踩坑清单

| # | 坑 | 说明 / 正确做法 |
|---|---|---|
| 1 | 以为 `mysqldump` 退出码 0 = 成功 | **实测它打印 `Error: ... PROCESS privilege` 却退出 0**。必须同时做 stderr 检查 + 产物完整性检查 |
| 2 | 忘加 `set -o pipefail` | `mysqldump \| gzip` 时 mysqldump 的失败被 gzip 掩盖 → 得到"合法的空备份" |
| 3 | 只看文件大小判断备份好坏 | 被打断的 dump 前面完全正常，**只有结尾缺 `Dump completed`** |
| 4 | 备份账号没 `PROCESS` 就报错 | 正确做法是 **`--no-tablespaces`**，而不是把 `PROCESS` 这种大权限给出去 |
| 5 | **crontab 里直接写 `%`** | **`%` 是特殊字符**（后的内容变成 stdin），必须转义 `\%` 或用不带 `%` 的命令（`date -Iseconds`） |
| 6 | cron 任务"手工跑正常、cron 不跑" | ① PATH 太短 ② `SHELL=/bin/sh` 不支持 bash 语法 ③ 文件权限不是 644/属主不是 root（**静默忽略**） |
| 7 | 以为 cron 文件放进去就生效 | 权限/属主/文件名带点/结尾无换行 → **静默忽略，不报错**。第一动作永远是 `ls -l` + `tail -f /var/log/syslog \| grep CRON` |
| 8 | `-mtime +7` 以为是 7 天 | `-mtime +N` = **N+1 天及以上**。保留 7 天要写 `+6` |
| 9 | `sudo zcat f \| mysql` | 管道里的 `mysql` 是**普通用户**。要 `sudo sh -c 'zcat f \| mysql'` |
| 10 | 备份文件权限 644 | 备份等于明文数据库，**必须 600** |
| 11 | 备份和数据放同一个文件系统 | 盘满/盘坏时两者一起没。**至少分开放**，生产要 3-2-1 |
| 12 | 备份脚本里写死密码 | 用 `--defaults-extra-file`（600）或 `mysql_config_editor` |
| 13 | `grep -c` 用来数"出现几次" | `-c` 数的是**行数**。数次数要 `grep -o \| wc -l` |
| 14 | `echo "!! ..."` | bash 把 `!!` 展开成上一条命令。字符串里别用 |
| 15 | 只备份不演练 | **没验证过的备份等于没有备份**。每月至少抽一个做恢复验证 |
| 16 | 以为 `DROP DATABASE` 会删权限 | 不会。授权按库名字符串匹配，恢复建库后**自动生效** |

## 七、命令详解（本项首次出现）

### 7.1 `mysqldump` 参数

| 参数 | 是什么 → 干什么 → 为什么这里用 |
|---|---|
| `--defaults-extra-file=` | 从这个文件读连接参数（用户/密码/主机）。**必须放在所有参数最前面** |
| `--single-transaction` | 开一致性事务快照（`START TRANSACTION WITH CONSISTENT SNAPSHOT`）→ **InnoDB 不锁表**还能拿一致数据 |
| `--quick` | 一行一行取，不把结果集缓进内存 → 大库必须 |
| `--routines` | 导存储过程和函数（**默认不导**，最常漏） |
| `--triggers` | 导触发器（默认开，显式写清） |
| `--events` | 导定时事件 |
| `--no-tablespaces` | 跳过表空间信息 → **不需要 `PROCESS` 权限** |
| `--databases db` | **复数**。会带上 `CREATE DATABASE` + `USE` → 恢复时不用指定库 |
| `--skip-extended-insert` | 每行一条 INSERT（体积大，但便于 `diff`/部分恢复）。**默认是合并** |
| `--master-data=2` / `--source-data=2` | 在备份里记录 binlog 位点（支持时间点恢复）→ 需 `REPLICATION CLIENT` |

### 7.2 压缩与校验

| 命令 | 是什么 → 干什么 → 为什么这里用 |
|---|---|
| `gzip -9 > f` | 最高压缩级别 → 13K vs 48K |
| `gzip -t f` | **只校验不输出**：检查 gzip 完整性 → 发现截断 |
| `zcat f` | 解压到 stdout（不落地中间文件） |
| `zcat f \| mysql` | 直接把 SQL 灌回数据库 → **恢复**的标准姿势 |
| `du -h f \| cut -f1` | `du` 看文件占用，`cut -f1` 取第一列（大小） |

### 7.3 Shell 脚本相关

| 命令 / 语法 | 是什么 → 干什么 → 为什么这里用 |
|---|---|
| `set -euo pipefail` | `-e` 出错即退；`-u` 未定义变量报错；**`-o pipefail` 管道任一环失败都算失败** |
| `${VAR:-默认}` | 有环境变量用它，否则用默认 → **让脚本可测试**（`DAYS=3` 改保留天数） |
| `mktemp` | 生成唯一临时文件名 → 并发时不互相覆盖 |
| `trap 'rm -f "$E"' EXIT` | 脚本退出时（成功/失败/被 kill）都执行清理 |
| `command -v xxx` | 检查命令是否存在 → 比 `which` 标准，不依赖外部程序 |
| `tee -a log` | 同时输出到屏幕和**追加**到文件 → 手工跑能看、cron 跑有记录 |
| `if ! cmd; then ... fi` | `!` 取反；**不能写成 `cmd && {...}`**，在 `set -e` 下行为易错 |
| `bash -n script` | **只做语法检查**，不执行 → 长脚本写完第一件事 |
| `install -m 755 src dst` | 复制 + 设权限 + 设属主，先写临时文件再 rename → 比 `cp+chmod` 安全 |

### 7.4 `find` 与时间

| 语法 | 是什么 → 干什么 |
|---|---|
| `find DIR -maxdepth 1 -type f -name 'p*'` | 只在当前层找普通文件，按名字模式 |
| **`-mtime +N`** | 修改时间**早于 N+1 天**（整 24 小时向下取整）→ 保留 7 天要写 `+6` |
| `-print -delete` | 先打印再删除（**顺序有意义**：先 print 才能看到删了什么） |
| `date -d "-3 days" +%F` | `-d` 支持自然语言日期（GNU 扩展）→ 造"假日期"文件用 |
| `touch -d "7 days ago" f` | 把文件的 mtime 改成指定时间 → **测时间逻辑的标准手法** |
| `cp -p` | 复制时**保留 mtime/权限** |
| `ls --time-style=long-iso` | 时间显示成 `2026-11-09 08:15`，比默认格式好读 |

### 7.5 cron 相关

| 语法 | 是什么 → 干什么 |
|---|---|
| `/etc/cron.d/<name>` | 5 时间字段 + **user** + 命令；属主 root、权限 644、名字别带点 |
| `* * * * *` | 分 时 日 月 周；`*` = 每个 |
| `30 2 * * *` | 每天 02:30 |
| **`\%`** | crontab 里 `%` 必须转义，否则后面变成命令的 stdin |
| `SHELL=` / `PATH=` | 覆盖 cron 默认的 `/bin/sh` 和极简 PATH |
| `sleep 80` | 让时间跨过至少一个整分钟，确保能观察到每分钟任务 |

### 7.6 其它

| 命令 | 是什么 → 干什么 |
|---|---|
| `grep -c` | 匹配的**行数** |
| `grep -o` | **只输出匹配部分**，每处一行 → 配合 `wc -l` 数次数 |
| `rm -f 'prefix_111[4-7]*'` | 字符类，匹配 `1114`~`1117` → 一条命令删多个 |
| `sudo sh -c 'cmd1 \| cmd2'` | 把**整条管道**交给 root 的 shell（管道/重定向由当前 shell 建立，`sudo` 只作用于紧邻的一个命令） |
| `tr '\n' ' '` | 把换行换成空格 → 把多行日志压成一行写进日志 |
| `basename path` | 只取文件名 |

| 验收项 | 结果 |
|---|---|
| 写脚本：`mysqldump` + 打包 + 按日期命名 + 保留 7 天 | ✅ `/usr/local/bin/mysql-backup.sh`（`755 root`），产物 `labdb_YYYYmmdd_HHMMSS.sql.gz`（600），`-mtime +6` 保留 7 天 |

**面试可用的一句话总结：**

> 我用 `mysqldump --single-transaction --no-tablespaces` 加 `gzip` 做了日备脚本，日期命名、保留 7 天（`find -mtime +6`）、日志分 `ok`/`FAIL`，用 `set -euo pipefail` 保证管道失败不会被 gzip 掩盖，并且做了三重校验：退出码、stderr 里有没有 Error、以及解压后结尾有没有 `Dump completed`。因为我实测发现 `mysqldump` 会"打印 Error 但退出码 0"、也会"文件看起来正常但结尾缺完成标记"。最后用 `DROP DATABASE` 做了最坏情况恢复演练，靠 `COUNT`+`SUM(id)`+时间范围三重指纹证明恢复的是同一批数据。
