## 一、目标与验收

**做：** MySQL 数据放 named volume；写一个容器数据备份脚本

**验收：** **删容器重建，数据还在**

**结论：** 达成，而且做了两种备份方案并**都做了恢复演练**：

| 方案 | 做法 | 产物 | 恢复结果 |
|---|---|---|---|
| **A 逻辑备份** | `docker compose exec -T db mysqldump … \| gzip > 宿主机文件` | **3.1K** | ✅ `DROP TABLE` 后完整恢复（`500 / 125250`） |
| **B 物理备份** | 一次性容器 `tar` 整个卷 | **6.3M** | ✅ 恢复成功（**但见第四节的风险说明**） |

**最有价值的认知**：**容器化没有改变备份的本质** —— 实验 13 学的 `--single-transaction`、`Dump completed` 校验、`-mtime` 轮转，一行不用改就能复用；变的只是"命令在哪执行、数据从哪出来"。

## 二、最终状态

### 2.1 卷

```bash
madrough@ubuntulearn:~$ sudo docker volume inspect lab18_lab18-mysql-data --format '{{.Mountpoint}}'
/var/lib/docker/volumes/lab18_lab18-mysql-data/_data

madrough@ubuntulearn:~$ sudo du -sh /var/lib/docker/volumes/lab18_lab18-mysql-data
209M    /var/lib/docker/volumes/lab18_lab18-mysql-data
```

**卷在 `/var/lib/docker/volumes/...`，而 `/var/lib/docker` 挂在 30G 的 `sdc1` 上**（实验 16 的成果）→ 数据落在扩容盘上。

### 2.2 备份产物

```bash
madrough@ubuntulearn:~$ sudo ls -lh /data/backup/lab19/
-rw-rw-r-- 1 madrough madrough 3.1K  lab18db_20261116_033711.sql.gz     ← 手工 A
-rw------- 1 root     root     3.1K  lab18db_20261116_040355.sql.gz     ← 脚本生成的
-rw-r--r-- 1 root     root     6.3M  vol_lab18_20261116_033826.tar.gz   ← 方案 B
```

**注意属主差异**：
- `mysqldump` 那个是 **`madrough`**（**宿主机 shell 的 `>` 重定向创建的**）
- `tar` 那个是 **`root`**（**容器里的 root 写进 bind mount 的**）← **实验 17 "容器别用 root" 的后果落地**

### 2.3 备份脚本 `/usr/local/bin/lab19-backup.sh`（`755 root`）

```bash
#!/bin/bash
set -euo pipefail
cd /home/madrough/lab18
D=/data/backup/lab19; K=7; P='<MYSQL_ROOT_PASSWORD>'
F="$D/lab18db_$(date +%Y%m%d_%H%M%S).sql.gz"
L=/var/log/lab19-backup.log
mkdir -p "$D"
docker compose exec -T db mysqldump -uroot -p"$P" --single-transaction --databases lab18db 2>/dev/null | gzip > "$F"
chmod 600 "$F"; gzip -t "$F"
zcat "$F" | tail -3 | grep -q 'Dump completed'
echo "$(date '+%F %T') ok $(du -h "$F" | cut -f1) $F" >> "$L"
find "$D" -name 'lab18db_*.sql.gz' -mtime +$((K-1)) -print -delete >> "$L"
```

**和实验 13 的四处差别（全是容器化带来的）：**

| 差别 | 原因 |
|---|---|
| **`cd /home/madrough/lab18`** | `docker compose` 要在 compose 文件所在目录执行（cron 的默认目录是 `/`） |
| **`docker compose exec -T db`** | 备份对象在容器里；**`-T` 关掉 TTY**（否则输出被污染） |
| `2>/dev/null` | 屏蔽容器内的密码警告 |
| `chmod 600` | 容器 root 写出的文件仍要显式收紧权限 |

### 2.4 cron

## 三、操作步骤

### 3.1 摸底 + 一条意外收获

```bash
# 身份：madrough @ ubuntulearn（普通用户；sudo 提权）
madrough@ubuntulearn:~$ cd ~/lab18 && sudo docker compose ps
NAME          CREATED          STATUS
lab18-db-1    23 hours ago     Up 2 minutes (healthy)
lab18-web-1   23 hours ago     Up 2 minutes
```

**容器 23 小时前创建，2 分钟前"自己起来了"** —— 这台机器重启过，**`restart: unless-stopped` 把它们拉回来了**。对照实验 16 那两个 `Exited` 的容器（默认 `--restart no`）→ **这是那条配置价值的直接实证**。

### 3.2 造可验证的数据

```bash
madrough@ubuntulearn:~$ mysql -h 127.0.0.1 -P 3310 -u root -p'<MYSQL_ROOT_PASSWORD>' -e "
SET SESSION cte_max_recursion_depth=10000;
USE lab18db;
CREATE TABLE IF NOT EXISTS t19 (id INT PRIMARY KEY, v VARCHAR(20));
INSERT INTO t19
WITH RECURSIVE s AS (SELECT 1 n UNION ALL SELECT n+1 FROM s WHERE n<500)
SELECT n, CONCAT('row-', n) FROM s;
SELECT COUNT(*) AS n, SUM(id) AS sum_id FROM t19;"
# n = 500    sum_id = 125250
```

**指纹：`COUNT(*)=500`、`SUM(id)=125250`。** 后面所有备份/恢复都用它验收。

### 3.3 基线：删容器重建，数据还在

```bash
madrough@ubuntulearn:~/lab18$ sudo docker compose up -d --force-recreate db
madrough@ubuntulearn:~/lab18$ sleep 25
madrough@ubuntulearn:~/lab18$ mysql -h 127.0.0.1 -P 3310 -u root -p'<MYSQL_ROOT_PASSWORD>' \
  -e "SELECT COUNT(*) AS n, SUM(id) AS sum_id FROM lab18db.t19;"
# 500 / 125250    ← 数据在
```

**`--force-recreate db` 只重建这一个服务**：可写层全新、**卷不动** → 数据还在。这就是"数据活过容器"的最小验证。

### 3.4 方案 A：`mysqldump`（逻辑备份）

```bash
madrough@ubuntulearn:~$ sudo mkdir -p /data/backup/lab19 && sudo chown madrough:madrough /data/backup/lab19
madrough@ubuntulearn:~$ cd ~/lab18
madrough@ubuntulearn:~/lab18$ sudo docker compose exec -T db mysqldump -uroot -p'<MYSQL_ROOT_PASSWORD>' \
  --single-transaction --databases lab18db | gzip > /data/backup/lab19/lab18db_$(date +%Y%m%d_%H%M%S).sql.gz
madrough@ubuntulearn:~/lab18$ zcat /data/backup/lab19/*.sql.gz | grep -c 'INSERT INTO'    # 1
madrough@ubuntulearn:~/lab18$ zcat /data/backup/lab19/*.sql.gz | tail -2
# -- Dump completed on 2026-11-16  3:37:11
```

**这条命令的"两侧分工"是本项最重要的理解：**

```
sudo docker compose exec -T db mysqldump …   |   gzip   >   /data/backup/…
└──── 在【容器内】执行，读的是容器里的库 ────┘   └──── 在【宿主机】执行 ────┘
                                              （压缩和落盘都在宿主机）
```

**容器里的数据通过 `stdout` 管道流到宿主机 —— 不需要往容器里挂任何目录。**

**`-T` 为什么不能漏**：`docker compose exec` 默认分配 TTY；**重定向到文件时，TTY 会插入控制字符/做换行转换** → 备份文件被污染。

### 3.5 方案 B：`tar` 整个卷（物理备份）

```bash
madrough@ubuntulearn:~$ sudo docker run --rm \
  -v lab18_lab18-mysql-data:/data:ro \
  -v /data/backup/lab19:/backup \
  alpine tar czf /backup/vol_lab18_$(date +%Y%m%d_%H%M%S).tar.gz -C /data .
```

**四个部分：**

| 部分 | 作用 |
|---|---|
| `docker run --rm` | 临时"搬运工"容器，用完即删 |
| `-v 卷:/data:ro` | 挂卷，**只读**（搬运工不该改数据） |
| `-v /data/backup:/backup` | 挂宿主机目录（备份落点） |
| `tar czf … -C /data .` | `-C` 先切目录、`.` 打包内容 → **归档里是相对路径**，恢复时不会覆盖到 `/data` 以外 |

**产物：`6.3M`**（209M 数据目录压缩后）。

**等价写法**：`docker run --rm --volumes-from lab18-db-1 …`（继承该容器的所有挂载，不用手写卷名，但会把所有挂载都带进来）。

### 3.6 恢复演练 A：`DROP TABLE` → 灌回去

```bash
madrough@ubuntulearn:~$ mysql -h 127.0.0.1 -P 3310 -u root -p'<MYSQL_ROOT_PASSWORD>' -e "DROP TABLE lab18db.t19;"
madrough@ubuntulearn:~$ mysql -h 127.0.0.1 -P 3310 -u root -p'<MYSQL_ROOT_PASSWORD>' -e "SELECT COUNT(*) FROM lab18db.t19;"
ERROR 1146 (42S02): Table 'lab18db.t19' doesn't exist

madrough@ubuntulearn:~/lab18$ zcat /data/backup/lab19/lab18db_*.sql.gz | sudo docker compose exec -T db mysql -uroot -p'<MYSQL_ROOT_PASSWORD>'
madrough@ubuntulearn:~/lab18$ mysql -h 127.0.0.1 -P 3310 -u root -p'<MYSQL_ROOT_PASSWORD>' \
  -e "SELECT COUNT(*) AS n, SUM(id) AS sum_id FROM lab18db.t19;"
# 500 / 125250    ✅
```

**恢复是备份的反方向**：`宿主机 zcat → stdout → 容器里 mysql（stdin）`。**同样不需要挂载。**

**不用指定库名**：dump 时用了 `--databases`，SQL 文件里自带 `CREATE DATABASE` + `USE`。

### 3.7 恢复演练 B：换掉整个卷

```bash
madrough@ubuntulearn:~/lab18$ sudo docker compose stop db
madrough@ubuntulearn:~/lab18$ sudo docker run --rm \
  -v lab18_lab18-mysql-data:/data -v /data/backup/lab19:/backup \
  alpine sh -c 'rm -rf /data/* && tar xzf /backup/vol_lab18_*.tar.gz -C /data && ls /data | head -5'
#ib_16384_0.dblwr
#innodb_redo
auto.cnf
madrough@ubuntulearn:~/lab18$ sudo docker compose start db
madrough@ubuntulearn:~/lab18$ sleep 30
madrough@ubuntulearn:~/lab18$ sudo docker compose ps db
lab18-db-1   Up 41 seconds (healthy)      ← 起来了
madrough@ubuntulearn:~/lab18$ mysql … -e "SELECT COUNT(*) AS n, SUM(id) AS sum_id FROM lab18db.t19;"
# 500 / 125250    ✅
```

**物理恢复的铁律：必须先 `stop db`。** 否则一边替换文件一边 mysqld 还在写 → 必然损坏。

## 四、原理

### 4.1 卷是什么（不是"特殊目录"，是"被登记过的目录"）

```
命名卷 = /var/lib/docker/volumes/<卷名>/_data   （Docker 管理，加了元数据登记）
```

| 特性 | 说明 |
|---|---|
| 生命周期 | **独立于容器**：`docker rm` 不删卷，`docker volume rm` 才删 |
| 初始化 | **首次挂到一个"空卷"时，Docker 把镜像里该目录的现有内容复制进去** ← MySQL 初始化依赖它 |
| 谁管理 | Docker（`docker volume ls / inspect / prune`） |
| 备份方式 | 只能通过**容器**访问（宿主机路径是 root 权限目录，且不该直接动） |

### 4.2 逻辑备份 vs 物理备份（本项的核心对比）

| 维度 | **逻辑（`mysqldump`）** | **物理（`tar` 卷 / `xtrabackup`）** |
|---|---|---|
| 产物 | SQL 语句 | 数据文件的字节副本 |
| 本项大小 | **3.1K** | **6.3M** |
| 一致性手段 | **`--single-transaction`（InnoDB 快照）** | 需要**锁表/停库**或 `xtrabackup` 的 LSN 机制 |
| 恢复粒度 | 可只恢复**一张表**、甚至几行 | **只能整库整盘** |
| 跨版本 | ✅ 能（8.0 dump 灌进 8.4 通常可以） | ❌ 只能同版本 |
| 速度 | 慢（要解析 SQL 重放） | 快（直接拷文件） |
| 大库（>100G） | 太慢、太耗 CPU | ✅ 唯一可行 |
| 适用 | 中小库、需要跨版本/挑表恢复 | 大库、要求最短停机 |

### 4.3 **热 `tar` 为什么不保证一致**（本项必须讲清的风险）

**InnoDB 的数据"在磁盘上"和"逻辑上已提交"不是一回事**：

```
内存里的 buffer pool（脏页，还没写回）
  + redo log（保证崩溃恢复）
  + undo log（回滚用）
  + 数据文件（可能落后于 redo）
  + binlog（复制/时间点恢复用）
```

这几者**互相依赖、必须成套**才是"某个时刻的一致状态"。而 `tar` 只是**按目录顺序读文件**，读的过程中数据还在变 → 你拿到的是**"文件 A 是 10:00 的、文件 B 是 10:03 的"** 的混合体。

**本项的结果必须诚实地标注：**

> **这次 `tar` 恢复成功了，是因为拍照那一刻数据库空闲**（没有写入、没有事务在跑），文件状态恰好一致。
> **这不能证明"热 tar 备份一致"** —— 只要拍的时候有写入，就可能拿到不一致的副本。
> **更危险的不是起不来，而是"起来了但少了几行"**，等你真用它恢复时才发现。
> **本次未复现不一致（属运气），所以这条风险是"原理 + 业界共识"，不是本项实测结论。**

**生产上的正确姿势：**

| 手段 | 说明 |
|---|---|
| **`xtrabackup`（Percona）** | 唯一推荐的 InnoDB 物理热备工具：读 redo、记录 LSN、恢复时回滚未提交事务 |
| `FLUSH TABLES WITH READ LOCK` + `tar` | 备份期间**全局只读**（业务会卡住），只适合小库/短窗口 |
| 停库后 `tar` | 最安全但要停机 |
| **LVM/文件系统快照**（`lvcreate --snapshot`） | 秒级一致性快照，企业常用 |

### 4.4 容器里的数据怎么"出来"（三种姿势）

| 姿势 | 命令 | 适用 |
|---|---|---|
| **① stdout 管道** | `docker compose exec -T db mysqldump … \| gzip > 宿主机文件` | **逻辑备份首选**（不挂载、不落中间文件） |
| **② 双挂载搬运** | `docker run --rm -v 卷:/data -v 宿主目录:/backup alpine tar …` | 物理备份/拷贝 |
| **③ `--volumes-from`** | `docker run --rm --volumes-from 容器 -v 宿主目录:/backup alpine tar …` | 不用知道卷名/容器内路径 |

**方向反过来就是恢复**（`宿主机 zcat → 容器 mysql`）。

### 4.5 为什么备份文件要"落地在宿主机"

**容器一删，它的文件系统就没了。** 所以：

| 写法 | 结果 |
|---|---|
| `docker exec db sh -c 'mysqldump … > /tmp/b.sql'` | ❌ **备份在容器的可写层里**，容器一删就没了 |
| `docker exec -T db mysqldump … > /host/path` | ✅ 落到宿主机（`>` 是宿主机 shell 干的） |
| `docker run -v 宿主目录:/backup … tar -f /backup/x.tar.gz` | ✅ 落到挂进来的宿主机目录 |

### 4.6 一致性验证要用"内容指纹"，不能只看行数

| 指标 | 能发现 |
|---|---|
| `COUNT(*)` | 行数对不对 |
| **`SUM(id)`** | **"行数对但内容错"**（比如恢复成了别的批次数据） |
| 时间范围 `MIN/MAX` | 数据是不是原时间段的 |
| 抽样看几行 | 字段值对不对 |

**本项全程用 `500 / 125250` 作为指纹。**

## 五、生产实践

### 5.1 备份策略：逻辑 + 物理 + binlog 三层

| 层 | 工具 | 频率 | 作用 |
|---|---|---|---|
| **全量物理** | `xtrabackup` | 每天 | 快速恢复整个实例 |
| **逻辑** | `mysqldump` | 每天/每周 | 跨版本迁移、挑表恢复、可读性好 |
| **增量** | `xtrabackup --incremental` | 每小时 | 缩小 RPO |
| **binlog** | 连续归档 | 实时 | **时间点恢复（PITR）**，能恢复到"误删前一秒" |

### 5.2 容器数据备份的四条硬规矩

| 规矩 | 原因 |
|---|---|
| **备份必须落到宿主机/远端** | 容器一删，容器内的文件就没了 |
| **逻辑备份用 `-T`** | 否则 TTY 污染输出 |
| **物理备份前先停服务或加锁** | 热拷贝不一致 |
| **备份文件 `chmod 600`** | 里面是全部数据；而且容器 root 写出来的属主是 root，权限要显式管 |

### 5.3 `restart` 策略与备份无关，但与"可用性"有关

```yaml
restart: unless-stopped
```

**本项实证**：机器重启后容器自动回来（`Up 2 minutes`，而 `CREATED 23 hours ago`）。**没有这条，重启后要人手工 `docker start`。**

### 5.4 备份要监控，而且要验证恢复

| 手段 | 说明 |
|---|---|
| 检查最新备份时间 | 超过 26 小时没新备份 → 告警 |
| 检查文件大小异常 | 突然从 3.1K 变 200 字节 → 失败 |
| **内容校验** | `gzip -t` + `Dump completed`（脚本里已有） |
| **定期恢复演练** | 抽一个备份恢复到临时实例，比对指纹 |
| **heartbeat/死信** | 备份成功后上报（如 healthchecks.io），**心跳消失即告警** → 能发现"任务根本没跑" |

### 5.5 卷的日常运维

| 任务 | 命令 |
|---|---|
| 看所有卷占用 | `docker system df -v` |
| 清未使用的卷 | `docker volume prune`（**危险**：会删没容器在用的卷） |
| 迁移卷 | `tar` 出来 → 在目标机建卷 → `tar` 进去 |
| 卷加密 | 在宿主机层做（LUKS）或用支持加密的存储驱动 |

### 5.6 安全：备份里是明文全库

| 项 | 做法 |
|---|---|
| 静态加密 | 备份文件加密（`openssl enc` / `age` / 对象存储 SSE） |
| 传输加密 | `scp`/`rsync -e ssh`/对象存储 TLS |
| 访问控制 | 备份目录 `700`，备份账号只读（实验 12 的 `bkp`） |
| 离线/不可变 | 对象存储 WORM、版本控制（防勒索加密备份） |

### 5.7 3-2-1 原则（实验 13 讲过，这里依然没做）

> **本项所有备份都在同一台机器的 `/data` 上** —— 机器丢了（或 `/data` 盘坏），数据和备份一起没。**这是本机实验环境的固有缺陷**，生产必须补异地/对象存储。

## 六、踩坑清单

| # | 坑 | 说明 / 正确做法 |
|---|---|---|
| 1 | `docker exec` 备份不写宿主机路径 | **备份落在容器可写层里**，容器一删就没了 |
| 2 | `docker compose exec` 不带 `-T` 就重定向 | TTY 会往输出里插控制字符 → **备份文件被污染**。**`-T` 必加** |
| 3 | `docker compose` 在错误目录执行 | 报 `no configuration file provided`。**脚本里先 `cd` 项目目录**，或用 `-f/-p` |
| 4 | cron 里跑 `docker` 报 `command not found` | cron 的 PATH 极简。**cron 文件里写 `PATH=`**，并用 `env -i` 提前验证 |
| 5 | **热 `tar` 数据库目录** | **一致性无保证**（本项"成功"属运气）。用 `xtrabackup`，或先停库/加锁 |
| 6 | 物理恢复前不停库 | 一边替换文件一边 mysqld 在写 → **必然损坏**。**先 `stop`** |
| 7 | 恢复时忘 `-C /data` 打包 | 归档里带绝对路径，恢复时可能覆盖到意外位置。**`tar -C 目录 .`** |
| 8 | 以为 `tar` 出来的备份属主正常 | 容器 root 写进 bind mount → **宿主机上属主是 root**。后续非 root 任务会踩权限 |
| 9 | 只验证"行数对了" | 行数对但内容可能错。**用 `COUNT + SUM(id) + 时间范围` 指纹** |
| 10 | 用宿主机低版本 `mysqldump` dump 高版本库 | 可能不兼容。**容器内自带同版本客户端，优先用它** |
| 11 | 备份只留一份在本机 | 盘坏/机器丢就全没。**3-2-1** |
| 12 | 从不做恢复演练 | **没验证过的备份等于没有备份** |
| 13 | `docker volume prune` 随手跑 | 会删掉"没有容器在用"的卷（含刚 `down` 掉服务的卷）→ **数据没了** |
| 14 | 忘记 compose 的 `restart` | 重启后容器不起（本项实证：对比实验 16） |

## 七、命令详解（本项首次出现）

### 7.1 容器内执行

| 命令 | 是什么 → 干什么 → 为什么这里用 |
|---|---|
| **`docker compose exec -T 服务 命令`** | 在运行中的服务容器里执行命令；**`-T` 禁用 TTY** | 备份输出要经过管道 → 必须 `-T` |
| `docker exec -T 容器 命令` | 同上（指定容器而非服务） | 没有 compose 时用 |
| **`docker compose exec -T db mysqldump … \| gzip > 文件`** | **容器内产生数据 → 宿主机的 gzip 和重定向接收** | 逻辑备份的标准姿势 |
| `docker run --rm -v A -v B 镜像 命令` | 起一次性容器，挂两个目录 | tar 备份/恢复的"搬运工" |
| `--volumes-from 容器` | 继承该容器的**所有**挂载 | 不用知道卷名和容器内路径 |

### 7.2 `tar` 相关

| 参数 | 说明 |
|---|---|
| `tar czf 归档 -C 目录 .` | `c` 创建 / `z` gzip / `f` 指定文件；**`-C` 先切目录**，`.` 打包内容 → 归档内是相对路径 |
| `tar xzf 归档 -C 目录` | 解包到指定目录 |
| `-p` | 保留权限（root 执行时默认） |

### 7.3 卷相关

| 命令 | 说明 |
|---|---|
| `docker volume ls` / `inspect` | 列表 / **看 `Mountpoint`（宿主机真实路径）** |
| `docker volume create/rm/prune` | 建/删/清（**`prune` 危险**） |
| **`--force-recreate`**（`compose up`） | 强制重建容器（**卷不动**）→ 验证数据持久化 |

### 7.4 环境隔离测试

| 命令 | 说明 |
|---|---|
| **`env -i /bin/bash -c '命令'`** | **清空所有环境变量**执行 → 模拟 cron 的空环境 |
| `env -i PATH=/usr/bin:/bin 命令` | 只给最小 PATH 执行 |

### 7.5 校验与指纹

| 命令 | 说明 |
|---|---|
| `gzip -t 文件` | 只校验 gzip 完整性 |
| `zcat 文件 \| tail -3 \| grep 'Dump completed'` | 内容完整的硬判据 |
| `grep -c 'INSERT INTO'` | 语句条数（`--extended-insert` 会合并成 1 条） |
| `mysql -e "SELECT COUNT(*), SUM(id) …"` | **指纹**，恢复后必对 |

## 八、验收记录

| 验收项 | 结果 |
|---|---|
| MySQL 数据放 named volume | ✅ 卷 `lab18_lab18-mysql-data`（`209M`，在 `/var/lib/docker/volumes/...`，落在 30G 的 sdc1 上） |
| **删容器重建，数据还在** | ✅ `compose up -d --force-recreate db` → **新容器（35 秒）**，数据仍是 **`500 / 125250`** |
| 写容器数据备份脚本 | ✅ `/usr/local/bin/lab19-backup.sh`（`755`）：`docker compose exec -T db mysqldump --single-transaction \| gzip` + `chmod 600` + `gzip -t` + `Dump completed` + `find -mtime +6` 轮转 + 日志；`/etc/cron.d/lab19-docker-backup` 每天 03:30 |
| 附加：两种备份方案对比 | ✅ 逻辑 **3.1K** vs 物理 **6.3M**；恢复粒度、跨版本能力都实测 |
| 附加：两次恢复演练 | ✅ A：`DROP TABLE` → `zcat \| exec -T mysql` → 指纹对上；B：停库 → 换卷内容 → 起库 → `healthy`、指纹对上（**但已标注"热 tar 成功属运气"**） |
| 附加：cron 环境验证 | ✅ `env -i` 模拟空环境执行，退出码 0，日志新增一条 |

**面试可用的一句话总结：**

> 我把 MySQL 放命名卷里，验证了 `--force-recreate` 重建容器后数据仍在。备份做了两种：逻辑用 `docker compose exec -T db mysqldump --single-transaction | gzip > 宿主机路径`（3.1K），物理用一次性容器 `-v 卷:/data:ro -v 宿主目录:/backup alpine tar`（6.3M），两种都做了恢复演练并用 `COUNT + SUM(id)` 指纹验证。关键认知是：**容器化没改变备份本质**——`--single-transaction` 和 `Dump completed` 校验照旧，变的只是"数据从哪出来"（stdout 管道，不需要挂载）；而 **`tar` 热备份不保证一致**（这次成功只是赶上数据库空闲），生产物理备份要用 `xtrabackup` 或先停库/加锁。另外 cron 里跑要 `cd` 到 compose 目录、写全 `PATH`，我用 `env -i` 提前验证过。
