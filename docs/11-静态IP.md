# 11 静态 IP（netplan）

> 实验日期：2026-11-07
> 环境：Ubuntu 24.04.5 LTS（`ubuntulearn`），**netplan.io 1.1.2-8ubuntu1~24.04.3**，渲染器 `systemd-networkd`
> 快照：`lab-11-开始`
> 关联：[10 自建 DNS](10-自建DNS.md)（本项把它的 DNS 配置**持久化**）、[09 防火墙](09-防火墙.md)（放行 53）、[05 systemd 服务](05-systemd服务.md)（`Restart=` 自愈）

## 一、目标与验收

**做：** 用 `netplan` 配静态 IP + 网关 + DNS；**改错一次再修回来**

**验收：** 重启网络后配置仍生效；能说清 **NAT 和桥接**的区别

**结论：** 全部达成，且过程中撞到一个**比静态 IP 本身更有价值的问题** —— 开机时 `systemd-resolved` 比 `dnsmasq` 早启动 5 秒，把自建 DNS 标记为"降级"后切回运营商 DNS，**重启后本地域名全部解析失败**（第五节）。

**IP 从 `192.168.9.128`（DHCP）改成 `192.168.9.50`（静态）。**

## 二、最终状态

### 2.1 生效的 netplan 文件

```bash
# 身份：madrough @ ubuntulearn
madrough@ubuntulearn:~$ cat /etc/netplan/90-lab11.yaml
```

```yaml
network:
  version: 2
  ethernets:
    ens33:
      dhcp4: false
      addresses:
        - 192.168.9.50/24
      routes:
        - to: default
          via: 192.168.9.2
      nameservers:
        addresses: [127.0.0.1]
        search: [lab.test, lab.local]
```

**目录里现在有两个文件：**

```bash
madrough@ubuntulearn:~$ ls -l /etc/netplan/
-rw------- 1 root root  64 Oct 22 09:26 50-cloud-init.yaml     # cloud-init 生成，dhcp4: true
-rw------- 1 root root 321 Nov  7 08:43 90-lab11.yaml          # 我们的，覆盖上面那份
```

| 文件 | 作用 |
|---|---|
| `50-cloud-init.yaml` | 出厂状态，只有 `dhcp4: true`。**没删**，因为它是 cloud-init 管的，删了可能被重新生成 |
| `90-lab11.yaml` | 我们的配置。**名字排序在 `50-` 之后，所以覆盖它**（netplan 按字典序合并，后面的赢） |

### 2.2 运行状态

```bash
# 身份：madrough @ ubuntulearn
madrough@ubuntulearn:~$ ip -4 addr show ens33 | grep inet
    inet 192.168.9.50/24 brd 192.168.9.255 scope global ens33

madrough@ubuntulearn:~$ ip route
default via 192.168.9.2 dev ens33 proto static
192.168.9.0/24 dev ens33 proto kernel scope link src 192.168.9.50

madrough@ubuntulearn:~$ resolvectl status | head -14
       DNS Servers: 127.0.0.1          # Global
Current DNS Server: 127.0.0.1          # Link ens33
       DNS Servers: 127.0.0.1
        DNS Domain: lab.test lab.local
```

**三个关键特征，缺一不可：**

| 特征 | 值 | 说明 |
|---|---|---|
| 地址里**没有 `dynamic`** | `scope global ens33` | 有 `dynamic` = DHCP 租来的；没有 = 静态配的 |
| 路由的 **`proto` 是 `static`** | `default via 192.168.9.2 ... proto static` | `proto dhcp` = 来自 DHCP；`proto static` = 来自 netplan |
| DNS **只有一个入口** | `127.0.0.1` | 见第五节，两个入口会导致"重启后降级" |

### 2.3 配套改动（都在本项做的）

| 改动 | 位置 | 原因 |
|---|---|---|
| dnsmasq 记录同步到 `.50` | `/etc/dnsmasq.d/lab10.conf` 的 3 条 `host-record` | IP 变了，DNS 记录还是 `.128` |
| dnsmasq 加第二上游 | 同上，`server=223.5.5.5` | DNS 冗余要坐在转发器内部 |
| dnsmasq 加自愈 | `/etc/systemd/system/dnsmasq.service.d/restart.conf` | `Restart=on-failure` + `RestartSec=2` |
| netplan 里写 `search: [lab.test, lab.local]` | `90-lab11.yaml` | 让 `.local` 也被路由到 dnsmasq（第六节） |

## 三、操作步骤（按真实顺序，含两次失败）

### 3.1 摸底

```bash
# 身份：madrough @ ubuntulearn（普通用户，sudo 提权）
madrough@ubuntulearn:~$ ls -l /etc/netplan/
madrough@ubuntulearn:~$ sudo cat /etc/netplan/*.yaml
madrough@ubuntulearn:~$ systemctl is-active systemd-networkd NetworkManager
madrough@ubuntulearn:~$ ip -4 addr show ens33; ip route
madrough@ubuntulearn:~$ resolvectl status | head -14
madrough@ubuntulearn:~$ networkctl status ens33 | head -12
madrough@ubuntulearn:~$ nmcli device status
```

**实测：**

| 命令 | 输出 | 结论 |
|---|---|---|
| `ls -l` | `50-cloud-init.yaml`，`-rw-------` | 权限合规（别人不可读）；是 cloud-init 生成的 |
| `cat` | 只有 `dhcp4: true` | 没有 `renderer:` → **默认 networkd** |
| `networkctl status` | `Network File: /run/systemd/network/10-netplan-ens33.network` | **networkd 在管 ens33** |
| `nmcli device status` | `ens33 ethernet unmanaged` | NetworkManager **完全不插手** |
| `resolvectl` | `DNS Servers: 192.168.9.2` | ⚠️ **实验 10 设的运行时 DNS 已经丢了**（见 3.3） |

> **两个渲染器都 `active` 是正常的**：`systemd-networkd` 和 `NetworkManager` 可以同时运行，各管各的网卡。**判断谁管 ens33 只能靠 `networkctl` / `nmcli`，不能靠 `is-active`。**

### 3.2 备份

```bash
# 身份：madrough @ ubuntulearn（普通用户，sudo 提权）
madrough@ubuntulearn:~$ sudo mkdir -p /root/lab11
madrough@ubuntulearn:~$ sudo cp -a /etc/netplan/50-cloud-init.yaml /root/lab11/50-cloud-init.yaml.orig
madrough@ubuntulearn:~$ sudo ls -l /root/lab11/
```

**为什么备份到 `/root/lab11/` 而不是 `/etc/netplan/`**：netplan 只读 `*.yaml`，放个 `.orig` 其实不会被读；但**把备份和生效配置放同一个目录，迟早有人搞混**。物理分开。

### 3.3 解剖 DHCP 租约（顺手发现"设置会丢"的原因）

```bash
# 身份：madrough @ ubuntulearn（普通用户，sudo 提权）
madrough@ubuntulearn:~$ sudo cat /run/systemd/netif/leases/2
```

```
ADDRESS=192.168.9.128
NETMASK=255.255.255.0
ROUTER=192.168.9.2
SERVER_ADDRESS=192.168.9.254
NEXT_SERVER=192.168.9.254
T1=15min
T2=26min 15s
LIFETIME=30min
DNS=192.168.9.2
DOMAINNAME=localdomain
CLIENTID=ff2b9434c100020000ab117be166ce6853cbe0
```

| 字段 | 含义 |
|---|---|
| `ROUTER` | 网关（`.2`），与 `ip route` 一致 |
| `SERVER_ADDRESS` | **DHCP 服务器**是 `.254`，**不是**网关 `.2` |
| `T1` / `T2` | 续租时刻：T1 = 50% 租期（15min）开始单播续租，T2 = 87.5%（26m15s）改为广播续租 |
| `LIFETIME` | 租约 30 分钟 |
| `DNS` / `DOMAINNAME` | DHCP 塞下来的 DNS 和搜索域 |

> **`T1=15min` 解释了实验 10 的遗留问题**：`resolvectl dns` 是运行时设置，**每 15 分钟续租都会重新下发 DNS 把它冲掉**。不是"重启才丢"，是"一刻钟丢一次"。

### 3.4 查 DHCP 地址池（决定静态 IP 选哪个）

```powershell
# 身份：Windows 宿主机（PowerShell，可能需要管理员）
PS C:\> Select-String -Path 'C:\ProgramData\VMware\vmnetdhcp.conf' -Pattern 'range|subnet' | Select-Object -First 10
```

```
C:\ProgramData\VMware\vmnetdhcp.conf:19:subnet 192.168.30.0 netmask 255.255.255.0 {
C:\ProgramData\VMware\vmnetdhcp.conf:20:range 192.168.30.128 192.168.30.254;   # VMnet1 仅主机
C:\ProgramData\VMware\vmnetdhcp.conf:37:subnet 192.168.9.0 netmask 255.255.255.0 {
C:\ProgramData\VMware\vmnetdhcp.conf:38:range 192.168.9.128 192.168.9.254;     # VMnet8 NAT
```

**结论：`192.168.9.0/24` 的动态池是 `.128`–`.254`，`192.168.9.50` 在池外 → 安全。**

**为什么必须查**：静态 IP 如果落在 DHCP 池里，DHCP 服务器可能把同一个地址分给另一台机器 → **地址冲突**（两台机器抢一个 IP，症状是"时通时不通"、`arp` 表里 MAC 来回跳）。这类故障极难查，因为配置看起来完全正确。

### 3.5 故意改错一次：网关写 `.99`

```bash
# 身份：madrough @ ubuntulearn（普通用户，sudo 提权写入）
madrough@ubuntulearn:~$ sudo tee /etc/netplan/90-lab11.yaml > /dev/null <<'EOF'
network:
  version: 2
  ethernets:
    ens33:
      dhcp4: false
      addresses:
        - 192.168.9.128/24
      routes:
        - to: default
          via: 192.168.9.99      # 故意写错：真网关是 192.168.9.2
      nameservers:
        addresses: [127.0.0.1, 192.168.9.2]
        search: [lab.test, lab.local]
EOF
madrough@ubuntulearn:~$ sudo chmod 600 /etc/netplan/90-lab11.yaml
madrough@ubuntulearn:~$ sudo netplan get all
```

**`netplan get all` = 安全的预检**：它只做"解析 + 合并 + 打印"，**不生成后端配置、不应用到运行系统**。用来确认"我的文件到底覆盖上了没有"。

**然后应用（这一步特意保留原 IP `.128`，所以 SSH 不会断）：**

```bash
# 身份：madrough @ ubuntulearn（SSH，普通用户，sudo 提权）
madrough@ubuntulearn:~$ sudo netplan try --timeout 300
```

> ⚠️ **`netplan try` 会阻塞在前台等回车**，所以要**另开一个 SSH 会话**测试。

**另一个会话里实测：**

```
ip route                →  default via 192.168.9.99 dev ens33 proto static   ← 错网关生效
ping -c2 192.168.9.2    →  通（0% loss）                                     ← 同网段，不需要网关
ping -c2 8.8.8.8        →  2 packets transmitted, 0 received, 100% loss      ← 跨网段，挂
dig www.lab.test        →  192.168.9.128                                     ← 本地域，不出网
dig www.baidu.com       →  180.101.51.40                                     ← ★ 竟然通
```

**`dig www.baidu.com` 居然成功**，这是本次最反直觉的结果：

> dnsmasq 的上游 `192.168.9.2` **就在同一个 `/24` 里，直连可达，不需要默认网关**。所以**网关错只影响"离开本网段"的流量**。
>
> **精确结论（生产可用的判据）**：
> - **能访问内网、不能上外网** → 默认路由 / 网关错
> - **连内网都访问不了** → 二层 / 地址 / VLAN / 网线的问题
>
> 两个症状指向完全不同的层，别混。

**回滚：在原窗口按 `Ctrl+C`。** 实测回滚后：

```
ip route        →  default via 192.168.9.2 ... proto dhcp      ← proto 从 static 变回 dhcp
ip -4 addr      →  inet 192.168.9.128/24 ... dynamic           ← 字面回到 DHCP
ls /etc/netplan →  90-lab11.yaml 还在（321 字节）
```

> **`netplan try` 的回滚只恢复"运行状态"，不删文件。** 回滚后磁盘上的错配置还在，**下次 `netplan apply` 会把它重新应用上去** —— 这是最容易让人"以为修好了其实没修"的状态。

### 3.6 改成正确的静态配置

```bash
# 身份：madrough @ ubuntulearn（普通用户，sudo 提权写入）
madrough@ubuntulearn:~$ sudo tee /etc/netplan/90-lab11.yaml > /dev/null <<'EOF'
network:
  version: 2
  ethernets:
    ens33:
      dhcp4: false
      addresses:
        - 192.168.9.50/24
      routes:
        - to: default
          via: 192.168.9.2
      nameservers:
        addresses: [127.0.0.1, 192.168.9.2]

EOF
madrough@ubuntulearn:~$ sudo chmod 600 /etc/netplan/90-lab11.yaml
madrough@ubuntulearn:~$ sudo netplan get all
```

**写完之后什么都不能跑** —— 文件里已经是 `.50`，任何 `apply` 都会切断 SSH。

### 3.7 在 VMware 控制台应用（**本项最关键的一步**）

**为什么不能在 SSH 里做**：`netplan try` 的第 ③ 步一应用，IP 就从 `.128` 变成 `.50`，SSH 的 TCP 连接立刻死掉；而第 ④ 步"等你按回车"需要**在运行这条命令的那个终端里**按 —— 终端已经没了，于是 120 秒后自动回滚。

**控制台 tty 不受影响**（本地终端，不经过网卡），所以能按到回车。

```
VMware 窗口 → Ctrl+Alt+Space → F1（切到 tty1）
ubuntulearn login: madrough
Password: <USER_PASSWORD>
```

```bash
# 身份：madrough @ ubuntulearn（VMware 控制台 · 本地 tty，不是 SSH）
madrough@ubuntulearn:~$ sudo netplan try --timeout 300
```

**实测：** 控制台打印倒计时后，从 Windows 新开终端 `ssh madrough@192.168.9.50` **可以登录** → 回控制台按回车 → **`Configuration accepted.`**

> **这条工程原则要记住：改网络接入层（IP / 路由）时，必须用"不依赖被改链路"的通道** —— 带外管理（IPMI / iLO / 云控制台 / VMware 控制台）。SSH 本身就是被改的那条链路，不能当自己的救生圈。

### 3.8 应用后的第一次验证

```bash
# 身份：madrough @ ubuntulearn（新 SSH 会话到 192.168.9.50）
madrough@ubuntulearn:~$ hostname -I
madrough@ubuntulearn:~$ ip -4 addr show ens33 | grep inet
madrough@ubuntulearn:~$ ip route
madrough@ubuntulearn:~$ ping -c2 -W2 8.8.8.8
madrough@ubuntulearn:~$ sudo ss -ulnp | grep ':53 '
madrough@ubuntulearn:~$ dig www.lab.test +short
```

**实测：**

```
192.168.9.50
inet 192.168.9.50/24 ... scope global ens33            ← 没有 dynamic
default via 192.168.9.2 dev ens33 proto static
64 bytes from 8.8.8.8: ... time=187 ms                 ← 出网恢复（对照上一轮 100% loss）
192.168.9.50:53    dnsmasq pid=1786                    ← ★ dnsmasq 自己跟着搬家了
dig www.lab.test +short  →  192.168.9.128              ← ★ 假记录！
```

**两个亮点：**

1. **`bind-dynamic` 兑现了**：没有任何人重启 dnsmasq，它自己从 `.128:53` 重绑到 `.50:53`。如果当初配的是 `bind-interfaces`（启动时只绑一次），这里就会死在旧地址上。
2. **DNS 记录变成假的**：`dig www.lab.test` 返回 `.128`，而这台机器已经不在 `.128` 上了 —— **IP 和 DNS 记录是两份独立的真相**，改一个必须同步改另一个。这种"解析成功但指向死地址"比"解析失败"更难查，因为每一步看起来都对。

### 3.9 同步 dnsmasq 的记录

```bash
# 身份：madrough @ ubuntulearn（普通用户，sudo 提权）
madrough@ubuntulearn:~$ sudo cp -a /etc/dnsmasq.d/lab10.conf /root/lab11/lab10.conf.pre-ip-change
madrough@ubuntulearn:~$ sudo sed -i 's/192\.168\.9\.128/192.168.9.50/g' /etc/dnsmasq.d/lab10.conf
madrough@ubuntulearn:~$ sudo diff /root/lab11/lab10.conf.pre-ip-change /etc/dnsmasq.d/lab10.conf
madrough@ubuntulearn:~$ sudo dnsmasq --test -C /etc/dnsmasq.d/lab10.conf
madrough@ubuntulearn:~$ sudo systemctl restart dnsmasq
```

**`diff` 实测输出（改动范围一目了然）：**

```
11,12c11,12
< host-record=www.lab.local,192.168.9.128
< host-record=ns.lab.local,192.168.9.128
---
> host-record=www.lab.local,192.168.9.50
> host-record=ns.lab.local,192.168.9.50
25c25
< host-record=www.lab.test,192.168.9.128
---
> host-record=www.lab.test,192.168.9.50
```

改完验证：`dig www.lab.test` → `192.168.9.50`，`dig www.lab.local` → `192.168.9.50`，`getent hosts www.lab.test` → 正常。

> **`.local` 这次为什么会通？** 因为 netplan 里写了 `search: [lab.test, lab.local]`。systemd-networkd 把不带 `~` 前缀的域名当作**既是搜索域、也是路由域**，于是 resolved 有了"`*.lab.local` 交给 ens33 的 DNS"这条规则，压过了它默认的"`.local` → mDNS"。**实验 10 里靠 `resolvectl domain` 临时解决的那件事，在 netplan 里写 `search:` 就持久化了。**

### 3.10 第一次重启 —— 撞上"开机竞速"

```bash
# 身份：madrough @ ubuntulearn（普通用户，sudo 提权）
madrough@ubuntulearn:~$ sudo reboot
```

**重启后实测（全部正常，除了 DNS）：**

```
uptime              → up 2 min
ip -4 addr          → 192.168.9.50/24，无 dynamic
ip route            → default via 192.168.9.2 proto static
ss -ulnp            → 192.168.9.50:53 + 127.0.0.1:53（dnsmasq pid 1513）
systemctl is-active → dnsmasq / nginx / ufw 全 active
ufw status          → [4] 53/udp、[5] 53/tcp 仍在
dig www.lab.test    → 空 ← ❌
```

**`resolvectl status` 泄了底：**

```
DNS Servers: 127.0.0.1 192.168.9.2
Current DNS Server: 192.168.9.2      ← 用的是 .2，不是我们的 dnsmasq
```

**根因（两条独立证据）：**

```bash
madrough@ubuntulearn:~$ systemctl show -p ExecMainStartTimestamp systemd-resolved dnsmasq
ExecMainStartTimestamp=Sat 2026-11-07 09:25:25 UTC        # systemd-resolved
ExecMainStartTimestamp=Sat 2026-11-07 09:25:30 UTC        # dnsmasq（晚 5 秒）
```

resolved 先起 → 探测 `127.0.0.1:53` → 没人应答 → **把这个服务器标记为不可用（降级）** → 切到 `.2` → **之后不主动切回**。

人工 `sudo systemctl restart systemd-resolved` 后立刻恢复（`Current DNS Server: 127.0.0.1`，`dig` 出 `.50`）→ 证实"降级后不自动恢复"。

### 3.11 修掉竞速：DNS 只留一个入口

```bash
# 身份：madrough @ ubuntulearn（普通用户，sudo 提权）
madrough@ubuntulearn:~$ sudo tee /etc/netplan/90-lab11.yaml > /dev/null <<'EOF'
network:
  version: 2
  ethernets:
    ens33:
      dhcp4: false
      addresses:
        - 192.168.9.50/24
      routes:
        - to: default
          via: 192.168.9.2
      nameservers:
        addresses: [127.0.0.1]
        search: [lab.test, lab.local]
EOF
madrough@ubuntulearn:~$ sudo netplan apply
```

**`netplan apply` 这次可以在 SSH 里跑**：地址没变（还是 `.50`），SSH 不会断。**判断标准是"这条命令会不会切断我自己的连接"，不是"它是不是网络配置命令"。**

**设计原则（本项最重要的结论之一）：**

> **客户端的 DNS 只指向一个入口，冗余要坐在"转发器"内部（dnsmasq 里写多个 `server=`），而不是让客户端去猜哪个上游还活着。**

两个上游挂在同一条链路上时，resolved **只能凭健康状态二选一**；选到不认识本地域的那个，本地域名就废。只留一个，它没有别的可切，dnsmasq 一起来就恢复。

### 3.12 给 dnsmasq 加第二上游 + 自愈兜底

先测公网 DNS 能不能直连：

```bash
madrough@ubuntulearn:~$ dig @223.5.5.5 www.baidu.com +short +time=2 +tries=1
www.a.shifen.com.
180.101.51.40
180.101.51.157
```

**通了** → 可以把 `223.5.5.5` 写进 dnsmasq 做冗余。

```bash
# 身份：madrough @ ubuntulearn（普通用户，sudo 提权）
madrough@ubuntulearn:~$ sudo cp -a /etc/dnsmasq.d/lab10.conf /root/lab11/lab10.conf.pre-upstream
madrough@ubuntulearn:~$ sudo tee -a /etc/dnsmasq.d/lab10.conf > /dev/null <<'EOF'

# ⑧ 第二个上游：阿里 DNS，做冗余
server=223.5.5.5
EOF
madrough@ubuntulearn:~$ sudo mkdir -p /etc/systemd/system/dnsmasq.service.d
madrough@ubuntulearn:~$ sudo tee /etc/systemd/system/dnsmasq.service.d/restart.conf > /dev/null <<'EOF'
[Service]
Restart=on-failure
RestartSec=2
EOF
madrough@ubuntulearn:~$ sudo dnsmasq --test -C /etc/dnsmasq.d/lab10.conf
madrough@ubuntulearn:~$ sudo systemctl daemon-reload
madrough@ubuntulearn:~$ sudo systemctl restart dnsmasq
madrough@ubuntulearn:~$ systemctl show -p Restart dnsmasq
Restart=on-failure
```

**dnsmasq 多上游的真实行为（别想当然）：**

| 配置 | 行为 |
|---|---|
| 默认（本实验） | **优先发给一个上游，超时/失败才换下一个**（failover） |
| `all-servers` | **并发问所有上游，取最快回复**（更快、更耗流量、难审计答案来源） |
| `strict-order` | **严格按顺序**，第一个不行才问第二个 |

**`Restart=on-failure` 的意义**：dnsmasq 现在是全机唯一 DNS 入口，它崩了整机就瞎。这是用实验 05 的知识给单点故障兜底。

## 四、原理

### 4.1 netplan 是什么：一个"翻译器"

```
/etc/netplan/*.yaml
        │  netplan generate（合并 + 校验 + 翻译）
        ▼
后端渲染器（二选一，由 renderer: 指定，默认 networkd）
   ├─ systemd-networkd → /run/systemd/network/*.network   （本机用这个）
   └─ NetworkManager   → /etc/NetworkManager/system-connections/*
```

**netplan 自己不是网络管理器**，它不碰网卡。这解释了三个现象：

| 现象 | 原因 |
|---|---|
| `netplan apply` 成功后**没有任何输出** | 它只是翻译 + 让渲染器重载 |
| 配置写了但网卡没变 | **写给了错的渲染器**（或者渲染器没重载） |
| `resolvectl` 能看到 DNS，`/etc/netplan` 里也有 | netplan 把 `nameservers` 交给了渲染器，渲染器再告诉 resolved |

**本机实测的判断方法**（不要靠 `is-active`，两个渲染器都可以是 active）：

```bash
networkctl status ens33 | head -12     # 有 Network File: /run/systemd/network/10-netplan-ens33.network → networkd
nmcli device status                    # ens33 显示 unmanaged → NetworkManager 不插手
```

### 4.2 YAML 合并顺序：后面的赢

```bash
ls /etc/netplan/
50-cloud-init.yaml     # dhcp4: true
90-lab11.yaml          # 我们的
```

**netplan 按文件名字典序合并，后面的覆盖前面的。** 所以要覆盖 `50-cloud-init.yaml` 必须用 `90-` 这种排后面的名字；用 `00-` 反而会被 `50-` 的 `dhcp4: true` 盖回去。

验证办法：`sudo netplan get all` —— 打印**合并后**的最终结果，不用猜。

### 4.3 netplan 关键字段

| 字段 | 含义 | 注意 |
|---|---|---|
| `dhcp4: false` | 关 IPv4 DHCP | 必须显式写，否则 cloud-init 的 `true` 会留着 |
| `addresses: [x.x.x.x/24]` | 静态地址 + 前缀 | **`/24` 不能省**，它决定同网段范围和自动路由 |
| `routes: - to: default / via:` | 默认路由 | **`gateway4:` 已废弃**（netplan 1.x），必须用 `routes` |
| `nameservers: addresses:` | 上游 DNS 列表 | **只写一个入口**（见 3.11） |
| `nameservers: search:` | 搜索域 | **不带 `~` 前缀时，既是搜索域也是路由域**（见第六节） |

### 4.4 DHCP 租约里的 T1 / T2

| 字段 | 含义 |
|---|---|
| `T1`（通常 50%） | 到这时候客户端**单播**向原服务器请求续租 |
| `T2`（通常 87.5%） | 还没续上就改为**广播**找任何 DHCP 服务器 |
| `LIFETIME` | 租约到期时间，到期还没续上就放弃地址 |

本机：`T1=15min / T2=26min15s / LIFETIME=30min`。

> **实用推论**：DHCP 环境下任何"手工改的运行时网络设置"（`resolvectl dns`、`ip addr add`、`ip route add`）**最长能活 T1（15 分钟）**。要持久就必须落到配置文件里。

### 4.5 NAT 与桥接（本项验收要求）

先看这台机器的真实结构：

```
Windows 宿主机
├─ 物理网卡 ─────→ 局域网（如 192.168.1.x）→ 路由器 → 外网
├─ VMnet8（NAT）192.168.9.0/24
│   ├─ 192.168.9.1    宿主机在这张虚拟交换机上的地址
│   ├─ 192.168.9.2    VMware NAT 设备 = 网关 + DNS 代理，负责地址转换
│   └─ 192.168.9.254  vmnetdhcp 服务，发租约（range .128–.254）
│         └─ 虚拟机 192.168.9.50
└─ VMnet1（仅主机）192.168.30.0/24
```

| | **NAT**（本机用的） | **桥接** | **仅主机** |
|---|---|---|---|
| 虚拟机在哪个网段 | VMware **私有网段** `192.168.9.0/24` | **和宿主机同一个局域网网段** | 只有宿主机能进的 `192.168.30.0/24` |
| 谁做地址转换 | **VMware NAT 设备（`.2`）** 把源地址改写成宿主机物理网卡地址 | **不需要**，虚拟机是局域网里的独立主机 | 不出去 |
| 局域网其他机器能直接访问吗 | ❌ 不能（除非配**端口转发**） | ✅ 能，像访问另一台真机 | ❌ 只有宿主机能 |
| IP 从哪来 | VMware `vmnetdhcp`（`.254`） | 局域网路由器 DHCP | VMware `vmnetdhcp` |
| 网关 | `192.168.9.2` | 局域网路由器 | 无（不出网） |
| 好处 | 不占公司网地址、不被扫描、IP 段自己说了算 | 能被同网段访问（多机集群、别人连你的实验机） | 完全隔离的测试网 |
| 坑 | 外面进不来，要配端口转发 | 会被当成新设备接入：可能触发 802.1X、被网管告警、**抢真实设备的 IP** | 出不了网 |

**一句话**：**NAT = 藏在私有网段里，出网时被伪装成宿主机；桥接 = 直接搬进局域网，和真机平起平坐。**

**NAT 模式下让外网进来的办法**：VMware「编辑 → 虚拟网络编辑器 → NAT 设置 → 端口转发」，把 `宿主机IP:8080` 映射到 `192.168.9.50:80`。

### 4.6 为什么改 IP 必须用带外管理

`netplan try` 的机制：

| 步骤 | 动作 |
|---|---|
| ① | 读 YAML，生成后端配置 |
| ② | 备份**当前运行配置**，启动 120 秒计时器 |
| ③ | **立刻应用新配置**（和 `apply` 一样，网卡当场变） |
| ④ | 前台阻塞，**等你在本终端按回车** |
| ⑤ | 回车 = 确认；`Ctrl+C` = 立刻回滚；超时 = 自动回滚 |

**关键在 ④**：回车必须按在**运行这条命令的那个终端**里。

```
改 IP → 第③步把 .128 换成 .50 → 那个 SSH 的 TCP 连接立刻死
     → 第④步没人按回车 → 超时 → 自动回滚
```

**它其实在保护你**（不回滚就真锁在门外了），**但代价是改 IP 这件事在 SSH 里永远做不成** —— 因为"能按到回车"这个前提，被"改 IP 会断连接"这个动作本身破坏了。

**控制台 tty 为什么可以**：本地终端不经过网卡，IP 变了它照样活着。

> **对照**：第 3.5 步（改网关、不改 IP）**可以在 SSH 里跑 `netplan try`**，因为 SSH 不断；第 3.7 步（改 IP）必须去控制台。**同一个工具，能不能用取决于"这条命令会不会切断你自己的连接"。**

**补充一个坑**：`netplan try` 的回滚**不删文件**。回滚后磁盘上的错配置还在，下次 `apply` 会重新应用上去 —— 它保护的是运行状态，不是磁盘配置。

### 4.7 resolved 的"服务器降级"

systemd-resolved 会给每个上游 DNS 服务器维护一个**健康状态**。启动时如果某个服务器探测失败（连接超时/拒绝），它会**降级**这个服务器，并改用其他可用的。

**危险点：降级之后不会很快自动恢复。** 本机的表现：开机后一直用 `.2`，本地域名全部解析失败，直到 `systemctl restart systemd-resolved` 才恢复。

**修法优先级：**

| 方案 | 做法 | 评价 |
|---|---|---|
| **A（本机采用）** | netplan 里 DNS **只写 `127.0.0.1`**，让 resolved 无路可退 | ✅ 简单、确定；冗余交给 dnsmasq 内部的多个 `server=` |
| **B（备选）** | 给 resolved 加 drop-in：`After=dnsmasq.service` + `Wants=dnsmasq.service` | 治"启动顺序"，但改系统核心单元的启动依赖，可能拖慢一大串服务，副作用大 |
| C（不可取） | 重启后手工 `systemctl restart systemd-resolved` | 不是修复，是忘掉 |

## 五、踩坑清单

| # | 坑 | 说明 / 正确做法 |
|---|---|---|
| 1 | 在 SSH 里 `netplan apply` 改 IP | **必断，且 `netplan try` 会超时回滚**。改 IP 一律走 VMware 控制台 |
| 2 | 以为 `netplan try` 回滚就万事大吉 | **它不删文件**。回滚后磁盘上还是错配置，下次 `apply` 又上去了 |
| 3 | 用 `00-` 前缀去覆盖 `50-cloud-init.yaml` | **方向反了**。netplan **后者覆盖前者**，要用 `90-` |
| 4 | 静态 IP 落在 DHCP 池里 | 会和 DHCP 分出去的地址**冲突**，症状是"时通时不通"。**先读 `vmnetdhcp.conf` 的 `range`** |
| 5 | 以为"网关错 = DNS 也挂" | **错**。上游 DNS 在同网段时直连可达，DNS 照常工作。**网关只影响跨网段流量** |
| 6 | 以为两个渲染器都 active 会打架 | 不会，各管各的网卡。**判断归属用 `networkctl` / `nmcli`，不用 `is-active`** |
| 7 | `netplan apply` 没输出以为失败 | 成功时**就是不输出**。要看结果去查 `ip` / `resolvectl` |
| 8 | 改完 IP 忘了改 DNS 记录 | `host-record` 里的 `.128` 变成假地址 → **解析成功但指向死地址**，比解析失败更难查 |
| 9 | DNS 写两个上游（`127.0.0.1` + `192.168.9.2`） | 开机竞速时 resolved 会**降级自建 DNS 并切到 `.2`，不自动切回** → 重启后本地域名全挂。**客户端只留一个入口，冗余放进 dnsmasq** |
| 10 | 手工 `resolvectl dns` 当持久配置 | **DHCP 每次续租（T1=15min）都会覆盖它**。持久化必须写 netplan |
| 11 | `netplan try` 里以为"回车才生效" | **回车前就已经生效了**，回车是"确认保留"。所以那 120 秒里系统跑的就是新配置 |
| 12 | `diff` 返回 1 以为命令失败 | **有差异时 `diff` 的退出码就是 1**，这是正常返回值 |
| 13 | `tee` 不带 `-a` 想追加 | 不带 `-a` 是**覆盖**。追加必须 `tee -a`，且**只能跑一次**，否则配置里出现重复行 |
| 14 | 改完 unit 忘了 `daemon-reload` | drop-in 放进去不 reload，`Restart=on-failure` 不生效（05 的教训） |
| 15 | 重启后不查 `uptime` 就宣布"重启验证通过" | 没有 `uptime` 你**无法证明**这次真的是新开机 |

## 六、命令详解（本项首次出现）

### 6.1 netplan 系列

| 命令 / 参数 | 是什么 → 干什么 → 为什么这里用 |
|---|---|
| `ls -l /etc/netplan/` | 看配置文件名和**权限位**。netplan 要求 `.yaml` **不能被其他人读**，否则每次 `apply` 警告 `Permissions ... are too open` |
| `netplan get all` | **解析 + 合并 + 打印**最终配置，**不生成后端配置、不应用到系统** → 改完先验"覆盖上了没有"的最安全手段 |
| `netplan try --timeout N` | 应用新配置 → **阻塞等回车** → 回车确认 / `Ctrl+C` 回滚 / N 秒超时回滚 → 改网络时的"试错保险" |
| `netplan apply` | 生成 + 应用到运行系统，**立即生效、不可回滚** → 只用于"确定不会断自己连接"的改动 |
| `netplan --version` | ❌ **不存在这个参数**。CLI 子命令只有 `apply/generate/get/info/ip/set/rebind/status/try`。查版本用 `dpkg -l netplan.io` |
| `dhcp4: false` | 关 IPv4 DHCP → 不关会和静态地址打架 |
| `addresses:` | 静态地址列表，**必须带前缀长度**（`/24`） |
| `routes: - to: default / via:` | 默认路由，替代废弃的 `gateway4:` |
| `nameservers: addresses:` | 上游 DNS 列表 → **只写一个**（见第五节第 9 条） |
| `nameservers: search:` | 搜索域。**不带 `~` 时既是搜索域也是路由域** → 这就是 `.local` 能被路由到 dnsmasq 的原因 |
| `renderer:` | 指定后端（`networkd` / `NetworkManager`）。**不写默认 networkd** |

### 6.2 网络状态查看

| 命令 | 是什么 → 干什么 → 为什么这里用 |
|---|---|
| `networkctl status ens33` | 看这块网卡**由哪个后端管**（`Network File:` 一栏直接给出 `/run/systemd/network/10-netplan-ens33.network`） |
| `nmcli device status` | 看 NetworkManager 眼里的设备状态。`unmanaged` = 它不插手 |
| `hostname -I` | 打印**本机所有 IPv4 地址**（空格分隔），最快确认"我现在是几" |
| `ip -4 addr` 里的 `dynamic` | 这个单词表示**地址来自 DHCP**。静态地址没有这个词 —— 这是区分"静态配成功了没"的最快判据 |
| `ip route` 里的 `proto dhcp` / `proto static` | 路由的来源。`dhcp` = DHCP 下发；`static` = netplan 配的 |
| `cat /run/systemd/netif/leases/2` | networkd 保存的**原始 DHCP 租约**（`2` 是 ens33 的 ifindex）→ 看 `ROUTER`/`SERVER_ADDRESS`/`T1`/`LIFETIME` |
| `systemctl show -p ExecMainStartTimestamp A B` | 打印单元的某个属性（这里是主进程启动时刻）→ **判断"谁先起来"的唯一硬证据** |
| `systemctl show -p Restart dnsmasq` | 确认 `Restart=` 的设置被读到（验证 drop-in 生效） |

### 6.3 文件操作与 YAML 工具

| 命令 / 参数 | 是什么 → 干什么 → 为什么这里用 |
|---|---|
| `cp -a 源 目标` | `-a`（archive）保留**权限、属主、时间戳、符号链接**并递归 → 备份配置**必须**用它，否则权限位被改成默认值 |
| `mkdir -p` | 目录已存在也不报错，缺的父目录一起建 |
| `chmod 600 文件` | 只有属主可读写。netplan 要求 `.yaml` 不能被人读 |
| `tee 文件 <<'EOF'` | 以 **root** 写文件；`> /dev/null` 丢掉屏幕回显；`<<'EOF'` 单引号禁止变量展开 → `sudo echo > file` 的权限问题的正解 |
| `tee -a 文件` | `-a` = **append 追加**（不加就是覆盖）。⚠️ 只能跑一次 |
| `sed -i 's/旧/新/g' 文件` | `s///` 替换，`g` 同一行全部替换，`-i` **就地改文件** → 批量改配置里的重复值 |
| 正则里 `\.` | `.` 是"任意字符"，`\.` 才是字面点号 → 匹配 IP 时必须转义 |
| `diff A B` | 逐行比较，`<` 是 A 有、`>` 是 B 有 → **改完先看改动范围**。**有差异时退出码是 1，不是失败** |
| `Select-String -Path X -Pattern 'a\|b'`（Windows） | PowerShell 的 grep。`\|` 是正则"或" → 从大文件里挑出 `range`/`subnet` 行 |

### 6.4 其它

| 命令 / 参数 | 是什么 → 干什么 → 为什么这里用 |
|---|---|
| `uptime` | 显示开机时长 → **证明"这次真的是新开机"的唯一手段**，重启验证必查 |
| `dpkg -l netplan.io` | 查包版本（`--version` 不存在时的替代） |
| `dig +time=N +tries=N` | 每次等 N 秒、最多重试 N 次 → 出网挂时避免 `dig` 卡十几秒 |
| `ping -c2 -W2` | `-c2` 发 2 个包；`-W2` 每个最多等 2 秒 → 不让 `ping` 卡住终端 |
| `ping -n 2`（Windows） | `-n` 是 Windows 的"次数"（Linux 是 `-c`），别搞混 |
| `curl.exe -sI` | `-s` 静默、`-I` 只要响应头 → 判断"服务活不活"最轻量 |
| `Restart=on-failure` / `RestartSec=2` | 非 0 退出或被信号杀死时重启，间隔 2 秒 → 给"全机唯一 DNS 入口"兜底（05 的知识） |
| `/etc/systemd/system/<unit>.d/*.conf` | **drop-in 目录**：不改软件包自带的 unit，只追加/覆盖几项 → `apt upgrade` 不会冲掉你的改动。**改完必须 `daemon-reload`** |
| `all-servers` / `strict-order` | dnsmasq 多上游的两种模式：并发问所有 / 严格按顺序。**默认是"优先一个，失败换下一个"** |

| Windows 客户端可访问 | ✅ `ping .50` 通、`Resolve-DnsName www.lab.test` → `.50`、`curl` → `200 OK` |
| 旧地址退役 | ✅ `ping 192.168.9.128` 100% 丢失 |

**面试可用的一句话总结：**

> 我把实验机从 DHCP 的 `.128` 改成静态 `.50`：先读 vmnetdhcp 的 `range` 确认 `.50` 在池外，避免地址冲突；用 `90-lab11.yaml` 覆盖 cloud-init 的 `50-` 配置（netplan 后者覆盖前者）；在 VMware 控制台用 `netplan try` 应用，因为改 IP 会切断 SSH，而 `try` 的确认回车必须按在本地终端。中间故意把网关写错一次，验证了"网关错只影响跨网段流量、同网段照常"，并观察了 `try` 的自动回滚。第一次重启后发现 `dig 本地域名` 失败，用 `systemctl show -p ExecMainStartTimestamp` 定位到是 `systemd-resolved` 比 `dnsmasq` 早启动 5 秒导致服务器被降级，最终把 DNS 收成单入口解决。
